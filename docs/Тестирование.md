[Обновления 0.1.6 и 0.1.7 → 0.1.8](validation/Обновление-до-0.1.8.md): все шесть реальных переходов прошли; база и настройки сохранены, старые установки очищены, последняя копия сохранена.

[Переход 0.1.6 → 0.1.7](validation/Обновление-0.1.6-до-0.1.7.md): данные сохранены; выявлена ошибка очистки обновлений в исходном комплекте со встроенной Java. Вариант без Java прошёл полностью. Исправление проверки полного комплекта подтверждено в 0.1.8.

[Проверка обновления 0.1.5 → 0.1.6](validation/Обновление-0.1.5-до-0.1.6.md): три реальных перехода через программу, база игроков и настройки сохранены.

Проверки запускаются из корня репозитория после [сборки программы](Сборка.md). Нужны Windows, PowerShell и JDK 17+; проверенная среда — JDK 25. Для проверки совместимости дополнительно нужна Java 8 x32.

Проверки создают отдельные профили в `build/tests` и **300 синтетических игроков**. Рабочая база пользователя и профиль старого TTWR в AppData не используются. Стандартные сценарии не обращаются к настоящему серверу игроков или GitHub: HTTPS имитируется внутри JVM. Первоначальная сборка может загружать зависимости.

## Основной запуск

```powershell
.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25'
```

JDK компилирует тесты с `--release 8` и по умолчанию запускает их своей Java. Для запуска тех же проверок на Java 8 x32:

```powershell
.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25' -JavaExe 'C:\Tools\jre8-x32\bin\java.exe'
```

`-JavaExe` меняет только среду выполнения тестов. JDK остаётся нужен для компиляции. Проверка Java x32 на Windows x64 не означает проверку работы на 32-разрядной Windows.

## Что проверяется

| Группа | Проверки |
|---|---|
| SQLite и список игроков | SQL-страницы, Unicode, параметры запросов, присваивания полей, фиксация и откат, текущие и исторические рейтинги, места, резервирование открытой БД, ошибочный импорт, смена пути, целостность |
| Закрытие программы | Нормальный выход, обработчик завершения Java, откат незавершённой транзакции, второе подключение и корректное поведение WAL/SHM |
| Переносимый профиль | Создание собственной `data`, пустая стартовая база, перенос абсолютных путей |
| Обновление списка по XML | Успех, отмена, ошибка и очистка временных файлов при имитации HTTPS |
| Обновление программы | Сравнение версий, допустимые адреса, SHA-256, пути ZIP, манифест, сохранение `data` и `runtime`, резервирование и откат при ошибке записи |
| Удаление устаревшего документа | Повторный запуск очистки, проверка резервной копии и её повреждения, сохранность БД, настроек, Java, остальных документов и WAL/SHM |

`WeakCacheRollbackChecks` отдельно моделирует очистку записи слабого кеша при откате, чтобы обнаруживать повторное появление `NullPointerException`. В проверках установщика отдельная JVM удерживает блокировку: установка должна дождаться закрытия программы.

## Проверки окна программы

```powershell
.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25' -Gui
```

Параметр `-Gui` открывает настоящее окно TTWR в отдельном тестовом профиле. Проверяются версия в статусной строке, пункт меню обновления, ручная проверка, загрузка имитированного выпуска и отмена установки через штатный диалог выхода. Также проверяется вызов очистки устаревшего документа при старте.

Тест сам отвечает на свои диалоги. Нужна доступная графическая сессия Windows. Некоторые обычные проверки исходного `Settings.Load` также используют сведения AWT о дисплеях; наличие запуска без `-Gui` не гарантирует совместимость со средой без графической сессии.

## Проверка установщика и перезапуска

Сначала соберите native-помощник с помощью Zig; укажите свой путь к компилятору:

```powershell
& 'C:\Tools\zig\zig.exe' cc -target x86-windows-gnu -Os '-Wl,--subsystem,windows' src/test/native/UpdateRestartProbe.c -o build/UpdateRestartProbe.exe
if ($LASTEXITCODE -ne 0) { throw 'Restart probe compilation failed' }

.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25' -Gui -RestartProbe build/UpdateRestartProbe.exe
```

Отдельный процесс установщика должен дождаться закрытия приложения, заменить файлы и запустить проверочный EXE. Параметры `-Gui`, `-RestartProbe` и `-JavaExe` можно совмещать. Именно GUI-проверки и проверка перезапуска на обеих Java включены в workflow выпуска.

## Проверка ZIP и запускателя

После создания обоих комплектов:

```powershell
.\scripts\verify-packages.ps1 -Java32Home 'C:\Tools\jre8-x32'
```

Сценарий создаёт отдельные распакованные копии в `build/release-check-*`. Он проверяет файлы по `checksums.json`, встроенную версию, отсутствие рабочей `data`, пустую стартовую SQLite-базу и выбор Java для обоих комплектов.

Для отдельной диагностики запускателя выполните на тестовой копии комплекта:

```powershell
.\ttwr-sqlite.exe --check-runtime
```

Параметр проверяет выбранную Java и SQLite без открытия основного окна. Он создаёт локальную `data` и журналы, поэтому не запускайте его в исходном образе `build/image`, который затем будет упаковываться. Исходники дополнительных native-проверок находятся в `src/test/native`.

## Результаты и разбор ошибок

Успешный `test.ps1` заканчивается сообщением `All tests passed` и путём к временному профилю. Каждый запуск использует отдельные каталоги тестовых классов и профиля. При сбое сохраните этот путь, вывод команды, версию Java и параметры запуска.

Сообщение SAX об ошибочном XML ожидаемо в отрицательном сценарии. О результате судите по завершению команды, а не только по наличию этого сообщения. Ошибка проверки останавливает сценарий.

Локальные профили, журналы, базы и ZIP исключены из Git. Проверку публичного дерева выполняйте отдельно:

```powershell
.\scripts\check-public-tree.ps1
```

## Реальное обновление через GitHub

`scripts/test-live-upgrade.py` — отдельный необязательный сценарий с настоящей загрузкой релиза и запуском старой программы. Для него нужны сохранённые оригинальные ZIP исходной версии, доступный целевой релиз, графическая сессия Windows и инструменты, указанные в справке сценария:

```powershell
python scripts/test-live-upgrade.py --help
```

Теги предыдущих версий удалены из репозитория. Для повторения переходов нужны заранее сохранённые оригинальные комплекты; их SHA-256 сверяются со значениями в сценарии. Не используйте для теста рабочую папку программы и не считайте имитацию HTTPS подтверждением реального перехода через GitHub.

Порядок автоматического запуска и публикации описан в [GitHub Actions](https://github.com/uranic2/ttwr-sqlite/blob/main/docs/Автоматическая-сборка-и-публикация.md).

## Проверки BL-04 и BL-07 в рабочей версии

`SinglePassImportChecks` сравнивает все столбцы импортированных записей с исходным `Player.LoadXML`: Unicode, CDATA, комментарии, инструкции обработки, первые и повторные поля, вложенные игроки, повторные ID, отрицательный ноль и статистика. Проверяются создание всех восьми вторичных индексов, ошибка в конце XML, неверный ID, внешние сущности, отмена и прерывание потока с сохранением прежней базы.

`UpdateStorageChecks` проверяет сохранение последней пригодной резервной копии, удаление более старых успешных установок и сохранность неудачных, незавершённых, неизвестных и повреждённых папок, пользовательских файлов, WAL/SHM и Java. Проверяется повторный запуск очистки, отказ при несовпадении установленной программы, подсчёт объёма и, при доступности, junction/символические ссылки. GUI-режим `storage` подтверждает автоматический вызов очистки после открытия окна и пункт меню занимаемого объёма.

Сравнительные замеры импорта и ограничения методики: [отчёт BL-04 / BL-07](validation/Проверка-BL-04-и-BL-07.md). `ttr.ImportBenchmark` — необязательный сценарий, который принимает путь к синтетическому XML и новой выходной БД; стандартные проверки его не запускают.

В 0.1.8 `UpdateStorageChecks` воспроизводит резервные копии с исходным манифестом полного комплекта и отсутствующей в копии `runtime`. Проверяются сохранение исходного манифеста и Java, отказ при отсутствии файла приложения, неверном SHA-256 и опасном пути под видом `runtime`. GUI-проверка `storage` использует такой же полный манифест. Сценарий реального обновления умеет исходные 0.1.6 и 0.1.7 и воспроизводит старую успешную установку с полным манифестом резервной копии.

## Прогресс и отмена загрузки обновления

`DownloadChecks` проверяет двухсекундное окно скорости, среднюю скорость, оценку времени, остановку передачи и фиксацию показателей после получения архива. Часы в расчётных сценариях задаются явно. Моделируются зависшие заголовки и тело ответа: чтение игнорирует прерывание потока и должно завершиться именно после отключения соединения. Проверены ранняя и поздняя отмена, удаление частичного ZIP и сохранность существующего файла и резервных копий.

При `-Gui` дополнительно запускается `DownloadUiChecks` с медленным имитированным HTTPS: кнопка отмены, Esc, крестик, успешная загрузка и обрыв соединения. Используется настоящее окно программы; проверяются поля прогресса и интервал 1000 мс, отсутствие временной папки, сохранность БД, настроек и старой резервной копии. В каждом профиле сохраняется `download-window.png` для проверки вида окна.

Результаты и ограничения проверки: [окно загрузки и отмена](validation/Прогресс-загрузки-и-отмена.md).

## Прогресс игроков и импорт TTWR (BL-11 / BL-13)

`test.ps1` включает `PlayerProfileChecks`, `PlayerStreamChecks`, `PlayerDownloadStatsChecks`, `DbPackageCrashChecks` и `DbPackageRecoveryFailureChecks`. Проверяются источник без записи, 301 XML-запись / 300 игроков, все поля игроков и scope, резервирование открытого SQLite, отмена сети/SQL, неизвестная длина, ошибочные файлы/ссылки/junction, откат после блокировки второго файла и восстановление в следующей JVM после принудительного завершения процесса. Повреждённая копия должна блокировать `PortableStart.prepareProfile`, сохраняя журнал и настройки.

С `-Gui` дополнительно запускаются `PlayerUpdateUiChecks` (кнопка/Esc/крестик, повтор, успех, неизвестный размер, обрыв, импорт из меню), `ProfileFirstRunUiChecks` (согласие/отказ) и GUI-состояние отказа восстановления. Импорт из меню проверяется со шрифтом 18 pt; контролируется отсутствие обрезания счётчика. Снимки сохраняются в `player-ui-*`. Для первого запуска задаётся явный синтетический источник, реальный AppData не читается.

Используйте обычные команды `test.ps1 -Gui -RestartProbe` на доступных Java x64/x32. [Полный отчёт и ограничения](validation/Проверка-BL-11-и-BL-13.md).

## Дата базы и статусная панель

DatabaseDateChecks воспроизводит разные даты в db.xml и db_last_updated.php, проверяет приоритет публикации, резервную/неизвестную дату, сохранение и повторное открытие, отмену/ошибку/откат и импорт локального профиля без подмены даты.

С -Gui запускается DatabaseStatusUiChecks в двух отдельных JVM на одном синтетическом профиле: обновление и перезапуск. Проверяются исходные значки jStatusDB (warning/ok/question), дата установленного каталога, сравнение секунд и игнорирование запоздавшего ответа. Публичный сервер не используется в автоматических тестах. [Результаты](validation/Дата-базы-и-статусная-панель.md).

## Запуск без интернета

[Отдельный прогон настоящего EXE](validation/Запуск-без-интернета.md): первый запуск, существующий профиль с 300 синтетическими игроками и сетевые тайм-ауты на Java 8/25 x64. Проверены доступность интерфейса, неизвестная свежесть базы, чтение локальных сведений, сохранность записей и штатный выход.
