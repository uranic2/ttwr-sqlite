# Автоматическая сборка и публикация

Workflow `.github/workflows/release.yml` собирает и проверяет оба Windows-комплекта. Есть два способа запуска:

| Запуск | Результат |
|---|---|
| Вручную: **Run workflow** | Сборка, проверки и ZIP в артефакте Actions; без публикации релиза |
| Отправка нового тега `vX.Y.Z` | Те же проверки, затем публикация обоих ZIP в GitHub Releases |

Обычный push ветки не запускает этот workflow. Тег должен точно совпадать с `v` + значением `VERSION`. Поддерживается стабильный формат `X.Y.Z`, без суффиксов предварительных версий.

## Проверить сборку без публикации

1. Отправьте подготовленные изменения в репозиторий.
2. Откройте [workflow сборки](https://github.com/uranic2/ttwr-sqlite/actions/workflows/release.yml).
3. Выберите **Run workflow**, нужную ветку и подтвердите запуск.
4. Дождитесь успешного завершения задачи `build`.
5. В разделе **Artifacts** скачайте `windows-release-bundles`.

Артефакт хранится 14 дней и содержит оба ZIP, `SHA256SUMS.txt` и `release-notes.md`. Для скачивания артефактов Actions требуется вход в GitHub; опубликованные комплекты в Releases доступны без аккаунта.

## Подготовить новый выпуск

Перед отправкой тега `validate-release.ps1` требует в README обе прямые ссылки на ZIP подготавливаемой версии. До завершения публикации новые ссылки могут быть недоступны; после выпуска проверьте скачивание без авторизации.

Используйте новую версию, которая ещё не публиковалась. Не восстанавливайте удалённые старые теги ради повторного выпуска существующих комплектов.

1. Измените `VERSION`.
2. Обновите текущую версию и добавьте обе прямые ссылки на будущие ZIP в `README.md`. В ссылках должны совпадать тег, версия и имя файла. Формат: `https://github.com/uranic2/ttwr-sqlite/releases/download/vX.Y.Z/ttwr-sqlite-X.Y.Z-system-java.zip` и такой же адрес с окончанием `-windows-x64.zip`.
3. Добавьте раздел `## X.Y.Z` в `CHANGELOG.md`. Его содержимое станет описанием релиза.
4. Проверьте изменения и закоммитьте их. Отправьте ветку с этим коммитом.
5. Создайте и отправьте тег именно на подготовленном коммите.

Из корня репозитория, после подготовки файлов:

```powershell
.\scripts\validate-release.ps1
.\scripts\check-public-tree.ps1

git add VERSION README.md CHANGELOG.md
git commit -m "Prepare next release"
git push origin main

$releaseVersion = (Get-Content VERSION -Raw).Trim()
.\scripts\validate-release.ps1 -Tag "v$releaseVersion"
git tag "v$releaseVersion"
git push origin "v$releaseVersion"
```

Если выпуск включает изменения исходников или других документов, включите их в коммит до создания тега. `validate-release.ps1` проверяет версию, ссылки README и раздел CHANGELOG; он также формирует локальный `releases/release-notes.md`.

## Что выполняется на GitHub

Задача `build` работает на `windows-2022`:

1. Проверяет версию, тег и публичное дерево файлов.
2. Устанавливает Temurin JDK 25 x64, JRE 8 x32 и JRE 25 x64. Загружает Zig по версии и SHA-256 из `config/native-toolchain.json`.
3. Собирает приложение и native-помощник проверки перезапуска. Java-зависимости и исходный `ttwr.dat` проверяются по lock-файлу.
4. Запускает обычные, GUI-проверки и проверку установщика с перезапуском на Java 25 x64 и Java 8 x32.
5. Создаёт оба ZIP и проверяет их содержимое, контрольные суммы, встроенную версию, выбор Java и пустую стартовую базу.
6. Загружает проверенные комплекты в артефакт Actions.

Только после успеха сборки и только при push тега выполняется отдельная задача `publish` на Ubuntu. Она использует `scripts/publish-release.py`: создаёт черновик, загружает ZIP, сверяет размеры и SHA-256 с метаданными GitHub, затем публикует релиз. Более старый выпуск не назначается последним поверх более нового.

Имена опубликованных файлов:

```text
ttwr-sqlite-X.Y.Z-system-java.zip
ttwr-sqlite-X.Y.Z-windows-x64.zip
```

SHA-256 также включаются в описание релиза. Рабочие базы, настройки и тестовые профили в комплекты не попадают.

## Ошибки и повторный запуск

- Если `build` завершился с ошибкой, публикация не начинается. Откройте первый упавший шаг и его журнал.
- При наличии диагностических журналов создаётся артефакт `build-failure-diagnostics` со сроком хранения 7 дней.
- При ошибке публикации проверьте задачу `publish` и состояние черновика в Releases. Загрузка может остаться частичной.
- Повторный запуск допустим для того же содержимого: существующие файлы должны совпасть по размеру и SHA-256. Скрипт не заменяет опубликованные ZIP и не принимает посторонние вложения.
- Если код или состав комплекта нужно изменить после публикации, выпустите новую версию с новым тегом. Не перемещайте опубликованный тег на другой коммит.

Java устанавливается по основной версии 25 или 8, поэтому обновления JRE могут менять состав и SHA-256 комплекта при сборке в другой день. Даже для того же коммита повторная сборка не обязана совпасть побайтно с опубликованным ZIP.

## Доступ и ограничения

Дополнительные секреты и личный токен не нужны: публикация использует временный `GITHUB_TOKEN`. В workflow права по умолчанию ограничены `contents: read`; `contents: write` есть только у задачи публикации. Используемые Actions закреплены полными SHA коммитов.

После успешной публикации workflow сохраняет три последних стабильных релиза и удаляет более старые релизы с вложенными ZIP и соответствующими тегами. Ветки не удаляются. Он также не проверяет реальное обновление из каждой ранее выпущенной версии через публичный GitHub: для этого требуется отдельная проверка с сохранёнными исходными комплектами.

Локальные команды и описание проверок: [сборка](Сборка.md), [тестирование](Тестирование.md).

## Хранение релизов

После успешного шага `Publish verified GitHub Release` запускается `scripts/prune-releases.py --published-tag "$RELEASE_TAG" --keep 3`. Публикации и очистка выполняются последовательно в одной группе concurrency задачи `publish`.

Сохраняются **три последних стабильных версии по номеру `vX.Y.Z`**, а не по строковой сортировке или времени создания тега. Например, после выпуска 0.1.9 останутся 0.1.7, 0.1.8 и 0.1.9. Черновики, предварительные выпуски и релизы с другими форматами тегов сохраняются отдельно и не учитываются в тройке.

Перед очисткой проверяются опубликованное состояние нового релиза и наличие обоих ZIP с размерами и SHA-256. Если сборка, публикация или проверка не прошли, очистка не выполняется. Ручная сборка без публикации также ничего не удаляет. Повторный запуск старого тега, который уже не входит в тройку последних версий, останавливает очистку.

Список релизов читается со всех страниц API. Перед удалением каждого кандидата политика проверяется повторно. Сначала удаляется старый релиз вместе с вложениями, затем только его тег в `refs/tags`; ветки и самостоятельные теги без удаляемого релиза не затрагиваются. Если тег переместился, он сохраняется, а задача сообщает ошибку. При сбое между удалением релиза и тега тег может остаться: точное имя удалённого релиза есть в журнале, оставшийся тег нужно проверить отдельно.

Количество задаётся параметром `--keep 3` в workflow. Дополнительный токен не нужен: используется `GITHUB_TOKEN` задачи с правом `contents: write`. Для предварительного просмотра предусмотрен `--dry-run`; этот режим выполняет только чтение API и выводит план. Проверки политики без сети запускаются командой:

```powershell
python -m unittest discover -s src/test/python -p 'test_release_retention.py'
```

Удалённые ZIP и ссылки на старые релизы перестанут быть доступны. Эта политика относится к GitHub Releases; срок хранения артефактов Actions и локальные файлы программы регулируются отдельно.
