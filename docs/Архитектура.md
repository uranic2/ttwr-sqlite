# Архитектура TTWR SQLite

Описание относится к текущему коду **версии 0.1.10**. TTWR SQLite — настольная Windows-программа для проведения турниров по настольному теннису. Она сохраняет модель турниров и интерфейс оригинального TTWR, но использует SQLite для каталога игроков, отдельную переносимую папку данных и собственное обновление программы.

Предыдущее устройство описано в документе [«Архитектура оригинального TTWR»](Архитектура-оригинального-TTWR.md). Главное отличие: раньше весь каталог игроков читался из XML в память; теперь программа получает нужные записи из SQLite.

## Как устроена программа

Основная часть написана на **Java**, окна и таблицы — на **Swing**. SQLite работает внутри процесса Java через JDBC-драйвер: устанавливать отдельный сервер базы данных не требуется.

У программы четыре основные части:

| Часть | За что отвечает |
|---|---|
| Запускатель `ttwr-sqlite.exe` | Находит подходящую Java и запускает приложение |
| Интерфейс | Показывает игроков, турниры, сетки и результаты; принимает действия пользователя |
| Модель и хранение данных | Ведёт игроков, участников, этапы и встречи; читает и сохраняет SQLite и XML |
| Обновления | Получает новый каталог игроков либо новую версию приложения; проверяет и применяет результат |

При запуске EXE сначала проверяет Java в соседней папке `runtime`, затем `JAVA_HOME`, `JRE_HOME`, PATH и реестр Windows. Нужна Java 8 или новее. Сам запускатель 32-разрядный, но запускает Java отдельным процессом, поэтому подходит и Java x32, и x64.

Перед открытием главного окна программа проверяет, не осталось ли незавершённой замены базы. Затем подготавливает локальный профиль. Новый комплект содержит пустую базу — 0 игроков; каталог заполняется загрузкой с сервера или импортом оригинального TTWR. При переносе папки программы основные пути данных привязываются к её новому расположению.

Главное окно `TTRClient` по-прежнему связывает действия пользователя с моделью турниров. `Tournament` содержит участников, этапы и встречи; `Player` описывает игрока, а `Member` — его участие в конкретном турнире. Сохранились варианты для пар и команд. Сетевые операции и запросы списка игроков выполняются в фоне, а результат отображается средствами Swing.

## Форматы и структуры хранения

Файлы приложения и пользовательские данные разделены. **Рабочий профиль находится в `data` рядом с EXE**. Профиль оригинального TTWR в AppData остаётся независимым.

| Путь относительно папки программы | Формат и назначение |
|---|---|
| `app/ttwr.dat` | JAR-архив с Java-классами, значками и встроенной версией программы |
| `app/lib` | Библиотеки приложения, в том числе JDBC-драйвер SQLite |
| `app/seed` | Пустая стартовая база и начальные XML-файлы для нового профиля |
| `runtime` | Необязательная встроенная Java; полный комплект содержит JRE x64 |
| `data/ttwr.cfg` | Настройки в XML: интерфейс, пути и параметры работы |
| `data/ttwr_data.xml` | Дополнительные данные приложения в прежнем XML-формате, когда они сохранены |
| `data/DB/Players.sqlite` | Рабочая SQLite-база игроков и исторических записей рейтинга |
| `data/DB/db.xml` | Заголовок базы: имя, дата и ссылки на файлы её составных частей |
| `data/DB/Regions.xml`, `Templs.xml` | Справочник регионов и шаблоны турниров в XML |
| `data/Tours` | Файлы турниров в XML, включая автосохранения |
| `data/Backup` | Резервные копии, в том числе комплекты DB перед заменой каталога |
| `data/stats` | Экспорт статистики |
| `data/updates` | Временные файлы и сохранённые копии обновлений приложения |

На SQLite переведён именно каталог игроков. Турниры, настройки, шаблоны и метаданные не стали таблицами одной общей SQL-базы.

### Что находится в SQLite

В основной таблице `players` одна строка описывает игрока в определённой области данных. Составной ключ **`(scope, id)`** позволяет хранить текущую запись и исторические значения одного игрока. `scope = current` означает действующий каталог; дополнительные области используются для снимков рейтингов на дату. Версия схемы — 2. Поддержка исторических scope в хранилище не означает автоматическую загрузку истории: унаследованная цепочка DBTours/RatingList содержит заглушки. Подробнее — [заглушки и неясности оригинала](Заглушки-и-неясности-оригинального-TTWR.md).

В строке находятся профиль игрока, рейтинг и его изменение, места, признаки новой или изменённой записи и две группы статистики. Для поиска и сортировки есть служебные ключи и индексы по имени, фамилии, рейтингу и местоположению. Таблица `metadata` хранит служебные пары «ключ — значение».

Список игроков получает **страницы по 100 записей**. Поиск, фильтры и сортировка выполняются SQL-запросами; весь каталог для показа таблицы не загружается в память. Совместимый старый метод получения полного массива сохранён для отдельных обращений, но основная таблица им не пользуется.

Подтверждённые изменения игроков сохраняются в SQLite. Для составных операций используются транзакции: изменения фиксируются вместе либо откатываются, после чего обновляются уже открытые объекты игроков. Обычное сохранение не переписывает полный `Players.xml`; XML нужен для обмена и экспорта.

SQLite использует режим WAL. Рядом с базой во время работы могут появляться `Players.sqlite-wal` и `Players.sqlite-shm`; ими управляет SQLite, вручную удалять их нельзя. При подтверждённом выходе подключения закрываются; предусмотрено также закрытие при завершении JVM. Копия открытой базы создаётся штатным механизмом SQLite Backup, который учитывает данные журнала.

## Как обновляется список игроков

Сервер по-прежнему предоставляет каталог в XML, но локальный результат записывается в SQLite. Это получение **полного каталога**, а не только изменений отдельных игроков.

1. Пользователь запускает обновление базы. Программа проверяет наличие новых неучтённых турниров и необходимость сохранить остальные изменения. Проверка свежести использует дату серверной базы; входной точкой загрузки служит `db.xml`.
2. Для операции создаётся отдельная временная папка `data/.players-operation-*`. Рабочий комплект не заменяется во время чтения сети.
3. Загружаются заголовок базы и указанные в нём XML игроков, регионов и шаблонов. Игроки читаются за один SAX-проход: записи сразу поступают во временную SQLite-базу, без дерева DOM всего каталога.
4. После загрузки записей создаются восемь вторичных индексов и проверяется целостность SQLite. Подготавливаются согласованные `Players.sqlite`, `Regions.xml`, `Templs.xml` и `db.xml`.
5. Перед применением резервируется весь прежний каталог DB. SQLite копируется через Backup API, вместе с историческими областями; готовая копия сохраняется в `data/Backup/DB-before-import-*`.
6. Подключения к заменяемой базе закрываются. В `data/db-package.pending` записывается журнал восстановления, затем заменяются четыре подготовленных файла и проверяются результаты записи.
7. Программа открывает новый комплект и обновляет таблицу игроков. Успех показывается после переключения базы и обновления списка. Временные файлы операции очищаются; резервная копия остаётся.

Окно показывает этап, объём XML, скорости, число прочитанных записей и прошедшее время. Показатели обновляются раз в секунду; текущая скорость считается за последние 2 секунды. При неизвестном размере нет процента и оценки оставшегося времени. Завершение чтения XML ещё не означает завершения индексации, проверки и замены базы.

Кнопка «Отмена», Esc и крестик используют общий механизм. До применения результата операция отменяется с ожиданием остановки фоновой работы и очистки. На коротком этапе замены и отката отмена недоступна. При ошибке замены предпринимается восстановление прежнего комплекта. Если процесс прервался, журнал проверяется при следующем запуске до открытия базы. Повреждённая копия или ошибка восстановления блокируют запуск с несогласованным комплектом; журнал и копия сохраняются для повторной попытки.


### Дата установленного каталога и статусная панель

Оригинальный TTWR хранит дату каталога в атрибуте `DB/@date` файла `DB/db.xml`, а в памяти — в `DBMain.date`. Формат — `d.M.yyyy-H:m:s`. Панель внизу главного окна показывает **дату установленной базы**, а не дату сервера и не время скачивания.

Дата сервера берётся из первой строки `db_last_updated.php`; при недоступном ответе используется `date` серверного `db.xml`. Сравнивается полная дата со временем: предупреждение появляется, если серверная дата строго больше локальной либо локальная неизвестна. При невозможности проверить серверную дату показывается вопрос, сохраняя текст известной локальной даты.

В оригинале после успешной загрузки диалог повторно получал дату публикации, присваивал её новому `DBMain.date`, а сохранение записывало её в локальный `db.xml`. В 0.1.10 при замене диалога этот шаг и обновление статуса были пропущены. Исправление в текущих исходниках восстанавливает их через `DatabaseDate` и `DatabaseStatus`: дата сохраняется в подготовленном комплекте до применения, ошибки/отмена не изменяют прежнюю дату; старый ответ фоновой проверки не может отменить новый статус.

При импорте локального профиля сохраняется его собственная дата. Свежесть относительно сервера проверяется отдельно. Файлы `Players.sqlite` и схема SQLite ради даты не меняются: совместимым хранилищем метаданных каталога остаётся `db.xml`.

Исследование, контрольные ответы сервера и проверки: [дата базы и статус](validation/Дата-базы-и-статусная-панель.md).

### Импорт из оригинального TTWR

Импорт использует тот же механизм подготовки, резервирования и замены. При первом запуске программа может предложить базу из `%APPDATA%/TTWR/DB`; позже источник выбирается через «База данных → Импорт профиля TTWR…». Сам по себе пустой каталог не считается первым запуском.

Нужны `db.xml` и три указанных в нём XML-файла. Оригинальный TTWR следует закрыть. Источник проверяется, копируется во временную папку и повторно сверяется перед применением. Проверенные XML регионов и шаблонов сохраняются без пересериализации. Каталог **заменяется целиком**, объединения игроков нет. Настройки, турниры, пароли, журналы и архивы оригинала не импортируются; источник не изменяется.

## Как обновляется программа

Это отдельная операция: она меняет приложение, сохраняя рабочую базу, настройки и турниры.

1. При запуске выполняется фоновая проверка стабильного релиза GitHub — не чаще одного успешного запроса в сутки. Ручная проверка доступна через «Справка → Проверить обновления программы…» и нажатие на версию в статусной строке.
2. После согласия загружается ZIP `system-java`. Он подходит и комплекту со встроенной Java: существующая `runtime` сохраняется. Черновики и предварительные выпуски не устанавливаются, понижение версии не выполняется.
3. Проверяются доверенные HTTPS-адреса, размер и SHA-256 ZIP, пути внутри архива, контрольные суммы файлов из `checksums.json` и встроенная версия Java-архива. До успешной проверки файлы программы не заменяются.
4. После подготовки отдельно запрашивается согласие на выход и установку. Программа выполняет обычный выход с запросами сохранения; отмена выхода отменяет установку.
5. Отдельный процесс установщика ждёт освобождения блокировки приложения, резервирует заменяемые файлы, устанавливает новый комплект и запускает EXE из прежней папки. При обычной ошибке записи предпринимается откат.

Установщик не заменяет пользовательскую `data` и не обновляет Java в `runtime`. Пути передаются помощнику с сохранением Unicode, поэтому поддерживаются кириллица и пробелы. Блокировка `data/application.lock` защищает замену файлов от одновременной работы приложения; важна блокировка ОС, а не само наличие этого файла.

Загрузка имеет окно прогресса и общий механизм отмены через кнопку, Esc и крестик. Очистка относится только к временной папке текущей загрузки. Если удалить файлы не удалось, программа сообщает их путь.

Результат установки, журнал и копия файлов приложения находятся в `data/updates/update-*`. После успешного открытия главного окна проверяются установленный образ и сохранённые обновления. Последняя пригодная папка обновления сохраняется целиком; более старые распознанные успешные установки очищаются. Неизвестные, повреждённые, неудачные, незавершённые папки и папки с посторонними файлами или ссылками остаются. Объём можно посмотреть через «Справка → Файлы обновлений…».

**Копия приложения в `data/updates/.../backup` не является копией рабочей базы.** Она предназначена для возврата файлов программы; каталог DB резервируется отдельно. При проверке копии полного комплекта допускается отсутствие `runtime`, поскольку Java остаётся в установленной папке.

Проверки SHA-256 подтверждают целостность по метаданным GitHub через HTTPS; отдельной цифровой подписи издателя нет. Принудительное завершение установщика или отключение питания посреди замены не гарантируют автоматический откат приложения. Это ограничение отличается от восстановления комплекта DB по журналу.

## Основные классы и связь с оригиналом

| Классы | Назначение |
|---|---|
| `PortableStart`, `PortablePaths` | Подготовка переносимого профиля, восстановление незавершённой замены DB и привязка путей |
| `TTRClient`, классы `ttr.UI` | Главное окно, редакторы и отображение игроков и турниров |
| `Tournament`, `TStage`, `Member`, `Game` и их варианты | Модель турнира, этапов, участников и встреч, сохранённая из оригинала |
| `DBMain`, `DBPlayers` | Общий комплект базы и совместимый доступ к каталогу игроков |
| `SqlitePlayersStore`, `SqlitePlayerMap` | SQL-запросы и адаптер старых обращений к коллекции игроков |
| `SqliteMutations`, `SqliteFieldSetters`, `SqliteLifecycle` | Сохранение изменений объектов, транзакции и закрытие подключений |
| `StreamingPlayers`, `StreamingPlayerWriter`, `SqlitePlayersIntegration` | Потоковый импорт и экспорт XML, подготовка SQLite |
| `PlayerUpdates`, `ProfileImports`, `PlayersUpdateSession`, `PlayerProfileSource` | Сетевое обновление и импорт каталога, проверка источника и владение временными файлами |
| `PlayersUpdateControl`, `PlayersProgress`, `DBUpdateDlg`, `DbPackageTransaction` | Отмена, показатели, окно прогресса и восстанавливаемая замена комплекта DB |
| `ProgramUpdates`, `ReleaseClient`, `UpdateInstaller`, `AppInstance`, `AppVersion` | Проверка релиза, загрузка, установка, блокировка приложения и встроенная версия |
| `DownloadStats`, `DownloadControl`, `UpdateDownloadDialog`, `UpdateStorage` | Показатели и отмена загрузки приложения, окно прогресса и хранение копий обновлений |

Репозиторий содержит новые помощники и восстановленные изменённые классы, но не все исходники оригинального TTWR. Остальные классы берутся из неизменённого `vendor/upstream/ttwr.dat`. При сборке `BuildSqliteTTWR` соединяет их с новыми классами и преобразует выбранные инструкции байткода: например, направляет прежние присваивания полей игроков в SQLite и подключает новые обработчики обновлений. Это позволяет сохранить работу старой модели турниров с новым хранилищем.
