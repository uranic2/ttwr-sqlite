# Почему исходный TTWR долго запускался и потреблял много памяти

## Как проблема выглядела для пользователя

**Исходная программа содержит список всех игроков, когда-либо участвовавших в турнирах, в XML-файле `Players.xml`. При каждом старте этот список целиком парсился и загружался в память через DOM.** Прежде чем пользователь мог перейти к подготовке турнира, программа читала файл, строила полное дерево XML и создавала объекты всех игроков.

По мере накопления участников список вырос примерно до 150 тысяч записей. При каждом запуске обрабатывались все эти записи, хотя для проведения конкретного турнира пользователю нужна лишь небольшая часть игроков. Это проявлялось в очень долгом запуске и высоком потреблении памяти.

Задержка сопровождалась большим потреблением памяти. Сам `Players.xml` занимал около 76 МБ, но его представление внутри Java требовало значительно больше: программа одновременно держала дерево XML, объекты игроков, строки и временные данные. Загрузка большого списка игроков создавала нагрузку на сборщик мусора и уменьшала запас памяти для интерфейса и турниров.

Проблема повторялась в других пользовательских действиях:

| Действие | Что происходило в исходной реализации | Последствие |
|---|---|---|
| Запуск с большой базой | Чтение и разбор всего XML, создание всех игроков и справочников | Ожидание загрузки до работы со списком игроков, высокий пик памяти |
| Обновление базы | Разбор полного XML и повторная сериализация во временный XML-файл | Дополнительные вычисления, запись большого файла и расход памяти |
| Обычное сохранение списка игроков | Создание полного XML-дерева и запись всех игроков | Даже небольшие изменения требовали полного прохода по списку игроков и перезаписи файла |

Таким образом, объём работы определялся размером **всей базы**, а не количеством игроков, с которыми пользователь работал в данный момент.



## Что обнаружил анализ программы

Исследование Java-классов показало, что список игроков читает `ttr.DBPlayers.LoadXML()` через `Utility.LoadXMLDocument()`. Загрузчик строил `org.w3c.dom.Document` для всего файла, а затем создавал из него объекты `Player` и помещал их в карту. На этом этапе одновременно существовали две формы одних данных: полный XML и список объектов Java.

Дополнительные расходы нашли в `DBPlayers.UpdatePlayerLocationList()`: для каждого игрока города, регионы и страны искались через `ArrayList.contains()`. Новые значения вставлялись в нужное место отсортированного списка, со сдвигом элементов. В исследованном списке игроков было 5308 городов, 795 регионов и 199 стран; повторные поиски и вставки становились заметной частью загрузки.

Загрузчик также отправлял уведомления прогресса для каждого игрока. В одном запуске насчитали 149 194 уведомления по записям и ещё 9312 по прочитанным байтам. Обработчики обновляли индикатор и его текст значительно чаще, чем требовалось пользователю.

Проверка записи выявила ту же зависимость от полного документа: `DBPlayers.SaveXML()` сначала формировал DOM всех игроков и лишь затем записывал его. В режиме обновления полученный XML дополнительно сериализовался в `Players.xml.tmp`.

Дисковые операции были крупными по объёму: исходная модель требовала чтения полного списка игроков при загрузке и полной записи при сохранении. .
