# BL-12. Разделить сборку на тестовую и стабильную

**Статус: запланировано.** Предлагаемый приоритет — **P2**.

## Цель

Разделить выпуск и обновление программы на два канала: стабильный для обычной работы и тестовый для проверки новых возможностей. Добавить в настройки выбор канала, чтобы пользователь мог получать тестовые версии без ручного поиска ZIP на GitHub.

В интерфейсе использовать название **«Канал обновлений»**. Канал определяется версией и типом опубликованного релиза. Организацию Git-веток можно выбирать отдельно: создавать отдельную ветку исходников для работы канала необязательно.

## Текущее поведение

В текущем коде поддерживаются стабильные версии `X.Y.Z`. `AppVersion` не принимает суффиксы тестовых сборок, а `ReleaseClient` отклоняет предварительные релизы. Workflow публикует оба ZIP по стабильному тегу версии; ручной запуск создаёт артефакты сборки без публикации релиза.

Поэтому одного переключателя в настройках недостаточно: нужно согласовать формат версий, публикацию, выбор обновления, установщик и хранение старых выпусков.

## Предлагаемая схема каналов

| Параметр | Стабильный | Тестовый |
|---|---|---|
| Назначение | Обычная работа с турнирами | Проверка новых функций и исправлений |
| Выбор по умолчанию | Да, в том числе для существующих профилей | Пользователь включает самостоятельно |
| Допустимые обновления | Стабильные релизы | Стабильные и тестовые релизы |
| Пример версии | `0.2.0` | `0.2.0-beta.1` |
| Пример тега | `v0.2.0` | `v0.2.0-beta.1` |
| Тип релиза GitHub | Обычный стабильный выпуск | Предварительный выпуск, `prerelease` |

Формат `-beta.N` предлагается как единый формат тестовых версий. Перед реализацией закрепить его в сценариях и документации. Номер `N` сравнивать как число: `beta.10` новее `beta.2`.

Черновики не предлагать ни в одном канале. Для тестового канала выбирать максимальную допустимую версию среди стабильных и тестовых выпусков. Например, стабильная `0.2.0` должна предлагаться поверх `0.2.0-beta.3`; выбор тестового канала при этом сохраняется для следующих обновлений.

## Настройки и интерфейс

1. Добавить в настройки поле **«Канал обновлений»** с вариантами **«Стабильный»** и **«Тестовый»**.
2. Рядом с тестовым каналом кратко пояснить, что он предназначен для проверки новых изменений и может содержать ошибки.
3. Сохранять выбор в переносимом профиле `data` рядом с программой. Отсутствующее или неизвестное значение трактовать как стабильный канал; старые настройки должны загружаться без ошибки.
4. После применения настройки сбрасывать ограничение повторной проверки для выбранного канала. Ручная проверка должна сразу использовать новый выбор.
5. Переключение канала само по себе не скачивает и не устанавливает программу. Сохраняется обычное предложение загрузки и отдельное подтверждение установки.
6. Если загрузка уже идёт, смену канала применять после её отмены и завершения очистки. Не смешивать результаты двух каналов и временные файлы разных операций.
7. В предложении обновления показывать полный номер и тип выпуска. В «О программе» отображать полный номер установленной сборки, включая `beta.N`, и её тип. Выбранный канал проверки показывать в настройках: он может отличаться от типа уже установленной сборки.

## Выбор версии и возврат на стабильный канал

Сравнивать версии по числовым компонентам и признаку предварительного выпуска, а не по строке, дате публикации или имени ZIP.

Ожидаемый порядок:

```text
0.1.9 < 0.2.0-beta.1 < 0.2.0-beta.2 < 0.2.0-beta.10 < 0.2.0 < 0.2.1-beta.1
```

| Установлено | Выбран канал | Доступно | Ожидаемое поведение |
|---|---|---|---|
| `0.1.9` | Стабильный | `0.2.0-beta.1` | Не предлагать тестовый выпуск |
| `0.1.9` | Тестовый | `0.2.0-beta.1` | Предложить обновление |
| `0.2.0-beta.2` | Тестовый | `0.2.0-beta.10` | Предложить обновление |
| `0.2.0-beta.3` | Любой | `0.2.0` | Предложить стабильный выпуск |
| `0.2.0-beta.3` | Стабильный | Только `0.1.9` | Сохранить установленную версию, объяснить отсутствие подходящего обновления |
| `0.2.0` | Тестовый | Только `0.2.0-beta.10` | Не понижать версию |

**Автоматическое понижение версии в эту задачу не включать.** Если пользователь переключился на стабильный канал, программа ждёт подходящий стабильный выпуск. Отдельный механизм возврата к более старой версии потребует проверки совместимости БД и настроек и собственного сценария восстановления.

## Сборка и публикация

- Оба канала должны создавать два ZIP: со встроенной Java x64 и без Java с поддержкой установленной Java x32/x64.
- Версия, тег, встроенный номер, описание релиза и имена ZIP должны совпадать. Например: `ttwr-sqlite-0.2.0-beta.1-system-java.zip` и `ttwr-sqlite-0.2.0-beta.1-windows-x64.zip`.
- Для обоих каналов обязательны действующие проверки Java x64/x32, интерфейса, установщика, манифестов и пустой стартовой базы.
- Тестовые комплекты публиковать как публичные предварительные релизы с файлами для скачивания. Артефакты ручного запуска Actions остаются отдельным способом проверки сборки.
- Тестовый выпуск не должен заменять последний стабильный релиз или его ссылки в основном разделе README. Ссылки на тестовые версии разместить отдельно с обозначением канала.
- Опубликованные файлы и теги не переиспользовать для другого содержимого. Для исправленной тестовой сборки увеличивать `beta.N`.
- Политику удаления старых выпусков применять отдельно к каждому каналу. Предлагается сохранять три стабильных и три тестовых релиза: серия тестовых сборок не должна удалять доступные стабильные комплекты. Значения закрепить в настройках сценария публикации.

## Выбор и установка обновлений

Для тестового канала получать список подходящих опубликованных выпусков с учётом страниц ответа. Не ограничиваться текущим запросом только последнего стабильного релиза. Некорректный или неполный выпуск не считать подходящим; в сообщении объяснять причину, чтобы не выдавать ошибку публикации за отсутствие обновлений.

Сохранять проверку доверенных HTTPS-адресов, размера ZIP, SHA-256, манифеста и встроенной версии. Полный номер `beta.N` должен проверяться и при распаковке, и в отдельном установщике, и при обработке резервных копий. Выбор тестового канала не ослабляет эти проверки.

Прогресс, скорости, оценка времени, отмена и очистка временной папки должны работать одинаково для обоих каналов. Проверка в фоне остаётся ограниченной по частоте, но её состояние учитывает выбранный канал.

## Сохранность данных

Переключение канала не меняет расположение профиля и не сбрасывает базу, настройки, турниры или встроенную Java. После установки сохраняется последняя пригодная резервная копия программы; её проверка должна понимать версии обоих каналов.

В тестовом выпуске, изменяющем схему БД или формат настроек, требуется явная миграция и проверенная копия изменяемых данных. Резервная копия файлов программы в `data/updates/.../backup` сама по себе не является резервной копией рабочей БД. Совместимость форматов и возможность восстановления должны быть описаны до публикации такого выпуска.

## План реализации

1. Закрепить формат тестовой версии и правила сравнения в `AppVersion`.
2. Обновить проверку версии, упаковку, workflow, публикацию и удаление старых релизов для двух каналов.
3. Добавить переносимое сохранение настройки с безопасным значением по умолчанию.
4. Обновить `ReleaseClient` и выбор кандидата; учитывать канал при фоновой и ручной проверке.
5. Проверить полный номер версии в `UpdateInstaller` и `UpdateStorage`, включая резервные копии тестовых сборок.
6. Добавить поле настроек и обозначения канала в интерфейсе.
7. Выполнить автоматические проверки и реальные обновления на отдельных синтетических профилях; обновить инструкции и README.

## Критерии готовности

- [ ] Новая и существующая установка по умолчанию получают только стабильные обновления.
- [ ] Выбор канала сохраняется после перезапуска и переноса папки программы.
- [ ] Тестовый канал получает подходящие тестовые и стабильные версии; черновики исключены.
- [ ] Все переходы из таблицы выше проверены; сравнение `beta.2` / `beta.10` числовое, автоматического понижения нет.
- [ ] Смена канала сбрасывает состояние проверки, не устанавливает обновление сама и не смешивается с активной загрузкой.
- [ ] Для каждого канала собираются и проверяются оба ZIP; скачивание опубликованных файлов доступно без аккаунта.
- [ ] Ошибочные метаданные, SHA-256 и встроенная версия не проходят установку независимо от канала.
- [ ] Отмена и обрыв связи очищают только временные файлы своей операции.
- [ ] База, настройки, турниры, Java и последняя пригодная резервная копия сохраняются при реальных переходах на Java 25 x64 и Java 8 x32.
- [ ] Публикация и очистка тестовых релизов сохраняют стабильные комплекты согласно отдельной политике хранения.
- [ ] Документация объясняет выбор канала, тестовые версии и порядок возвращения к стабильным выпускам.
