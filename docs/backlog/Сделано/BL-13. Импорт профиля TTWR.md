# BL-13. Импорт профиля TTWR

**Статус:** реализовано в 0.1.10 совместно с BL-11. [Результаты проверок](../../validation/Проверка-BL-11-и-BL-13.md).

Ниже сохранена постановка, уточнённая по исходникам 0.1.9. Указания об отсутствии импорта в прежней версии являются историческим контекстом.

## Исходная постановка

1. Создать процедуру импорта профиля TTWR: скопировать из `%APPDATA%\TTWR\DB` файлы игроков, `Templs.xml`, `Regions.xml` и создать SQLite-базу из XML игроков.
2. Вызывать эту процедуру при первом запуске.
3. Добавить пункт меню **«База данных → Импорт профиля TTWR»**.

В исходном тексте файл игроков назван `player.xml`. В проекте используется `Players.xml`; фактическое имя входного XML задаётся элементом `PlayerDB` заголовка `db.xml`.

## Цель и границы

Перенести локальную базу оригинального TTWR без повторного скачивания игроков. Исходный профиль остаётся независимым и используется только для чтения.

В этой задаче «импорт профиля» означает перенос **базы из папки DB**. Настройки `ttwr.cfg`, турниры, архивы, резервные копии, журналы и пароли не переносятся. Импорт заменяет локальных игроков, шаблоны и регионы после подтверждения пользователя; объединение каталогов и разрешение конфликтов записей не входят в задачу.

## Источник и результат

Источник по умолчанию — `%APPDATA%\TTWR\DB` текущего пользователя Windows. Разрешить выбрать другую папку DB, например из сохранённой копии профиля. Назначение — `data/DB` рядом с `ttwr-sqlite.exe`.

| Источник | Результат |
|---|---|
| `db.xml` | Локальный `data/DB/db.xml` с сохранением имени и даты базы, если они заданы, и ссылками на локальные файлы |
| XML игроков из `PlayerDB` (обычно `Players.xml`) | Преобразование в `data/DB/Players.sqlite` существующим потоковым импортом |
| XML шаблонов из `TemplDB` (обычно `Templs.xml`) | Проверка и копирование в `data/DB/Templs.xml` |
| XML регионов из `RegionList` (обычно `Regions.xml`) | Проверка и копирование в `data/DB/Regions.xml` |

Для первой реализации требовать все четыре составляющие. При отсутствии файла или ссылки на него сообщать об ошибке без частичного импорта и без подстановки файлов текущей базы. В выходном заголовке `PlayerDB` должен указывать на `Players.sqlite`, остальные ссылки — на соответствующие локальные XML.

Имена входных файлов читать из заголовка. Принимать только локальные файлы внутри выбранной папки DB; отклонять абсолютные пути, выход через `..`, сетевые URL и ссылки/junction за её пределы. Источник и назначение не должны совпадать или перекрываться.

## Пользовательские сценарии

### Первый запуск

1. До создания стартового профиля определить, является ли запуск первым. Отсутствие игроков само по себе не считается первым запуском.
2. Если старый профиль найден, предложить импорт с указанием источника и состава переносимых данных. Начинать только после согласия пользователя.
3. После успешного импорта открыть главное окно с перенесённой базой.
4. При отсутствии источника или отказе продолжить обычный запуск с пустой стартовой базой. После успешной первоначальной настройки автоматически импорт больше не предлагать.
5. При ошибке или отмене разрешить повторить выбор либо продолжить с пустой стартовой базой. Существующие пользовательские файлы не заменять стартовыми.

Неполная существующая `data` не считается новым профилем: сохранить действующую защиту от её автоматической перезаписи.

### Импорт из меню

1. Открыть **«База данных → Импорт профиля TTWR…»**. Показать обнаруженный источник и возможность выбрать другую папку DB.
2. Проверить комплект. Показать источник, назначение и предупреждение о замене игроков, шаблонов и регионов. Настройки и турниры сохраняются.
3. При открытом турнире или несохранённых изменениях предложить штатно сохранить и закрыть их. При отказе не начинать импорт. Исключить параллельные изменения базы и другие операции импорта/обновления.
4. После подтверждения создать резервную копию заменяемого комплекта DB и выполнить импорт.
5. Переключить приложение на новую базу, обновить таблицу игроков и справочники. Показать количество импортированных игроков и путь к резервной копии, если она создавалась.

Повторный импорт требует нового подтверждения и выполняется по тем же правилам, без слияния записей.

## Выполнение и сохранность данных

- Не создавать SQLite, временные файлы и журналы рядом с исходными XML. Предложить закрыть оригинальный TTWR; при изменении источника во время подготовки прервать операцию с предложением повторить её.
- Подготовить отдельный временный комплект внутри локальной `data`. Использовать существующий SAX-импорт за один проход, без DOM всего каталога. Сохранить совместимость декодера, создание индексов после загрузки и проверку целостности SQLite.
- До замены проверить заголовок, игроков, шаблоны, регионы и согласованность ссылок. Не полагаться только на успешное открытие SQLite.
- При замене существующей базы создать согласованную резервную копию всего заменяемого комплекта DB, включая все области `scope`, и проверить возможность её открытия. Копирование открытого SQLite-файла без учёта WAL недопустимо. Ошибка резервирования останавливает импорт.
- Применять только полностью подготовленный результат. Замена нескольких файлов не атомарна: предусмотреть откат при ошибке и восстановление после прерывания процесса. Приложение не должно открывать смесь старых и новых файлов.
- Корректно закрывать подключения перед заменой, затем обновлять хранилища и живые объекты. Постоянные WAL/SHM вручную не удалять. Настройки, турниры и другие каталоги `data` не заменять и не очищать.
- Чтение, преобразование и копирование выполнять вне потока Swing. Показывать этап и количество обработанных игроков; процент — только при известном полном объёме.
- Кнопка «Отмена», Esc и крестик используют общий механизм. Отмена доступна до применения результата; короткий этап замены/отката защищён от отмены и явно обозначен в интерфейсе.
- После отмены дождаться остановки фоновой работы и очистки временных файлов своей операции, затем разблокировать интерфейс. Резервные копии и файлы других операций сохраняются. При ошибке очистки или восстановления показать путь оставшихся файлов и дальнейшее действие; не сообщать об успехе.

## Критерии приёмки

Автоматические проверки используют синтетические профили в отдельных временных папках. Реальные AppData и рабочая `data` пользователя не используются.

| Сценарий | Ожидаемый результат |
|---|---|
| Первый запуск: источник найден / отсутствует / пользователь отказался | Импорт без согласия не выполняется; обычный запуск доступен |
| Повторный запуск; существующая пустая либо неполная `data` | Нет повторного автоматического предложения и автоматической перезаписи файлов |
| Корректный комплект с нестандартными именами XML в заголовке | Все поля игроков, шаблоны и регионы перенесены; локальный заголовок открывает SQLite |
| Кириллица и пробелы в путях, Unicode и CDATA в XML | Пути и данные обработаны без потерь |
| Повторный импорт в непустую базу с историей | Замена только после подтверждения; резервная копия открывается и содержит прежние текущие и исторические записи |
| Нет файла, повреждён XML, ошибка в конце XML, недопустимая ссылка | Понятная ошибка с указанием файла; прежний комплект не изменён |
| Отказ в доступе, нехватка места, изменение источника | Импорт прерван; исходный профиль и прежняя локальная база пригодны для работы |
| Отмена при чтении, копировании, построении индексов и перед применением | Нет частичного результата; временные файлы очищены после остановки работы |
| Ошибка замены или завершение процесса между заменами файлов | Откат либо восстановление при следующем запуске; смешанный комплект не открывается |
| Импорт из меню и последующий перезапуск | Новые данные доступны; SQL-поиск и страницы по 100 игроков работают; настройки и турниры сохранены |

Сохранность источника и файлов вне заменяемого комплекта проверять по хешам. Проверить Java 8 x32 и доступную Java x64 на Windows; GUI-сценарии первого запуска, подтверждения и отмены — в графической сессии. При реализации выполнить сборку и `scripts/test.ps1`, включая `SinglePassImportChecks`, `WeakCacheRollbackChecks` и `SqliteShutdownChecks`.

## Ориентиры реализации

- [PortableStart.java](../../../src/main/java/ttr/PortableStart.java) — первоначальная настройка; учитывать порядок создания стартового профиля.
- [PortablePaths.java](../../../src/main/java/ttr/PortablePaths.java) — переносимые пути. Метод `getenv("APPDATA")` перенаправляет старые обращения; для поиска оригинального профиля нужен настоящий `System.getenv("APPDATA")`.
- [DBMain.java](../../../src/main/java/ttr/DBMain.java) — заголовок и связи файлов базы.
- [SqlitePlayersIntegration.java](../../../src/main/java/ttr/SqlitePlayersIntegration.java) — преобразование XML. Передавать путь результата во временном локальном комплекте, чтобы не создавать SQLite рядом с исходником.
- [StreamingPlayers.java](../../../src/main/java/ttr/StreamingPlayers.java) — совместимый декодер игроков.

После реализации обновить [инструкцию пользователя](../../Руководство-пользователя.md), [архитектуру](../../Архитектура.md), CHANGELOG и [указатель бэклога](../Список-задач.md). До реализации инструкция пользователя описывала отсутствие автоматического импорта. Результаты проверок и ограничения сохранить в `docs/validation/`; наличие этой задачи не означает, что импорт уже доступен.
