# Проверка и установка обновлений программы

Начиная с версии 0.1.2, TTWR SQLite проверяет новые стабильные выпуски в [GitHub Releases](https://github.com/uranic2/ttwr-sqlite/releases). Аккаунт GitHub не требуется. Это обновление самой программы; обновление списка игроков по XML остаётся отдельным действием в меню «База данных игроков».

## Для пользователя

При запуске выполняется фоновая проверка, не чаще одного успешного запроса в сутки. Если доступна новая версия, появляется предложение загрузки. Ошибки фоновой проверки не мешают работе. Вручную проверить можно через **«Справка → Проверить обновления программы…»**; ручная проверка не ограничена суточным интервалом.

Номер SQLite-версии отображается и в правом нижнем углу главного окна. Нажатие на него также запускает ручную проверку. Прежняя проверка обновлений оригинального TTWR отключена: обновления программы берутся из репозитория SQLite-модификации.

Проверены и отключены также загрузка старого установщика и обработчики её завершения.

После согласия загружается комплект `system-java`. Он подходит и для версии со встроенной Java: существующая папка `runtime` сохраняется. Java автоматически не обновляется. На время загрузки основное окно недоступно; сетевые операции выполняются в фоне с тайм-аутами соединения и чтения.

В версии 0.1.9 окно загрузки показывает процент, скачанный и общий объём в КБ (1024 байта), скорость за последние **2 секунды**, среднюю скорость за весь сеанс загрузки, прошедшие секунды и оценку оставшихся. Показатели обновляются **раз в секунду**. До получения достаточных данных или при нулевой текущей скорости оценка оставшегося времени обозначается «—». После получения архива время и скорости загрузки фиксируются; отдельная строка сообщает о проверке и подготовке файлов.

**«Отмена»**, Esc и закрытие окна крестиком прерывают соединение и загрузку, затем удаляют ZIP и все временные файлы именно этой операции. Пока очистка не завершена, окно показывает её состояние; после этого можно продолжить работу или запустить проверку заново. Существующие резервные копии и незавершённые установки других операций не удаляются. Если удалить временные файлы не удалось, показывается сообщение с их папкой; успешная очистка не заявляется.

После проверки файлов программа отдельно предлагает закрытие и установку. Затем выполняется штатный выход TTWR с обычными запросами сохранения. Отмена выхода отменяет установку. Автоматическое сохранение турниров и остальные правила штатного выхода TTWR не изменены.

Отдельный установщик ждёт завершения программы, создаёт резервную копию заменяемых файлов и устанавливает обновление. При обычной ошибке записи предпринимается откат. После успеха запускается `ttwr-sqlite.exe` из той же папки.

Пользовательские база и настройки в `data` не заменяются. Установщик меняет только разрешённые файлы программы, стартового комплекта и документации. Рабочая база в `data/DB` отличается от пустой стартовой базы в `app/seed`.



## Если возникла ошибка

- Без интернета или при ограничении запросов GitHub продолжайте работать и повторите ручную проверку позже.
- Повреждённый ZIP, несовпадение контрольных сумм или неожиданные пути в архиве отменяют установку до замены программы.
- Программа должна находиться в доступной для записи папке. Права администратора установщик автоматически не запрашивает.
- Результат установки, журнал и резервная копия сохраняются в `data/updates/update-…`: `status.txt`, `installer.log`, папка `backup`.
- Если файлы установились, но автоматический запуск не удался, запустите EXE вручную.
- При неудачном откате закройте программу, сохраните всю её папку отдельно и восстановите файлы из `backup` в те же относительные пути. Папку `data` не заменяйте.

В версии 0.1.7 добавлена политика хранения обновлений. Через несколько секунд после успешного открытия главного окна в фоне проверяются файлы установленного образа и резервных копий по SHA-256. Последняя подходящая папка обновления сохраняется целиком, включая `backup`, ZIP, образ и журнал. Более старые распознанные успешные установки очищаются.

Без совпадающего установленного образа и пригодной последней резервной копии очистка не начинается. Неудачные, незавершённые, неизвестные и повреждённые папки остаются для диагностики. Папки со ссылками, junction или посторонними файлами, в том числе пользовательской `data`, не удаляются. Каталог `retired-files` с копиями устаревшего документа также сохраняется.

В меню **«Справка → Файлы обновлений…»** можно посмотреть занимаемый объём и папку резервной копии. Объём относится ко всему доступному хранилищу обновлений; связанные внешние каталоги не обходятся. Не удаляйте файлы вручную во время загрузки или установки. Отменённые и неудачные загрузки по-прежнему удаляются по возможности автоматически; это отдельная очистка собственного временного каталога загрузки.

С версии 0.1.5 при запуске удаляется один известный устаревший документ из `docs`, оставшийся после установки старых версий. Сначала создаётся проверенная резервная копия в `data/updates/retired-files`. Такая миграция срабатывает и при обновлении через старый установщик 0.1.2 или 0.1.4. База, настройки, WAL/SHM и прочие документы не удаляются. Если копирование или удаление не удалось, исходный документ остаётся, причина записывается в журнал, программа продолжает работу.

Обрыв питания или принудительное завершение установщика посреди замены не гарантируют автоматический откат. При такой ситуации используйте резервную копию либо распакуйте полный комплект заново, сохранив `data`.

## Для разработки и выпуска релизов

Проверяется `GET /repos/uranic2/ttwr-sqlite/releases/latest`. Черновики и предварительные версии не устанавливаются. Поддерживаются версии `X.Y.Z` и теги `vX.Y.Z`; сравнение числовое, понижения версии нет. Источник: [GitHub Releases API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release).

Релиз должен содержать `ttwr-sqlite-X.Y.Z-system-java.zip` с полем `digest` вида `sha256:…` в ответе API. Проверяются размер и SHA-256 архива, `checksums.json` каждого файла и встроенная версия `app/ttwr.dat`. Допускаются только HTTPS-адреса проекта и доверенные серверы перенаправления GitHub. Это проверка целостности через HTTPS и метаданные GitHub, а не отдельная цифровая подпись издателя. Источник: [GitHub Release Assets API](https://docs.github.com/en/rest/releases/assets#get-a-release-asset).

Установка использует копию старого Java-архива в каталоге обновления, поэтому выполняющийся помощник не блокирует замену основного архива. Java запускается из той же среды, что использовало приложение. Блокировка `data/application.lock` удерживается приложением до завершения JVM; установщик ждёт её освобождения до двух минут и удерживает во время замены. Файл блокировки может оставаться после выхода — значение имеет блокировка ОС, а не наличие файла.

С версии 0.1.3 пути передаются помощнику в UTF-8/Base64, а `updater.dat` загружается по относительному имени из рабочей папки. Это сохраняет кириллицу и другие символы, отсутствующие в системной кодировке Windows. Если установщик 0.1.2 из-за этого не запускается, первый переход на 0.1.3 нужно выполнить вручную с сохранением `data`.

Если изменяется структура комплекта, обновите список разрешённых файлов в `UpdateInstaller`. Если новая версия потребует более новую Java, текущий механизм, сохраняющий `runtime`, нужно изменить до выпуска такого релиза.

Версия 0.1.1 ещё не содержит этого механизма. На 0.1.2 с неё нужно перейти вручную; автоматическая проверка будет доступна для последующих выпусков.
