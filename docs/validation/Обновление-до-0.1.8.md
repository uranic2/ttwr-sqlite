## Исправление

В 0.1.7 проверка резервной копии полного комплекта требовала все 345 записей исходного манифеста, включая 320 файлов Java. Установщик сохраняет `runtime` в исходной папке программы и не копирует её в `backup`, поэтому очистка ошибочно останавливалась. [Результаты проверки 0.1.7](Обновление-0.1.6-до-0.1.7.md) сохранены отдельно.

В 0.1.8 `UpdateInstaller.verifyBackup()` допускает отсутствующие в резервной копии записи только под `runtime/`. Их пути и формат SHA-256 проверяются. Все файлы приложения остаются обязательными и проверяются по SHA-256; исходный манифест не переписывается. Проверка скачанного образа остаётся строгой и не допускает включение `runtime` в ZIP автоматического обновления.

`UpdateStorage` использует этот режим только для резервных копий. По-прежнему сохраняется последняя пригодная копия, а при повреждении или отсутствии файла приложения очистка не начинается. Неизвестные и неудачные установки, пользовательские файлы, ссылки и junction не включаются в удаление.

## Реальная проверка через программу

Каждый запуск использовал новую отдельную папку и оригинальные ZIP 0.1.6 либо 0.1.7 с проверенными SHA-256. В профиле созданы 301 синтетический игрок, одна историческая запись, метаданные, 16 нестандартных настроек и контрольные файлы в `Tours` и `Backup`.

В каждой копии воспроизведены две старые успешные установки. Их образы и резервные копии взяты из сохранённых оригинальных ZIP. Одна старая копия содержит полный манифест с `runtime`, но без самой Java в `backup` — так дополнительно воспроизводится проблемный состав. Это подготовленные тестовые остатки установок, а не два дополнительных сетевых обновления.

Также подготовлены неудачная и незавершённая установки, посторонние заметки и архив устаревшего документа, которые требуется сохранить.

Запускался исходный EXE старой версии. Java-agent нажимал штатные кнопки Swing и наблюдал окно без преобразования классов. Программа сама получала сведения о релизе с публичного GitHub, скачивала опубликованный ZIP 0.1.8, проверяла его, штатно закрывалась, устанавливала обновление и запускала 0.1.8. Ответы сервера не подменялись; авторизация в загрузчик программы не добавлялась.

После появления окна 0.1.8 тест ждал её автоматическую очистку. Наблюдатель не вызывал очистку вместо программы и не удалял папки сам. Только после проверки результата программа штатно закрывалась.

## Подтверждённые результаты

- Во всех случаях сохранены все строки и столбцы `players` и `metadata`: 301 текущий игрок и одна историческая запись рейтинга. Unicode, статистика, рейтинги и служебные значения совпали.
- Логический SHA-256 БД до и после: `375643510deb1ac9efa37b7e2178622a768036f70127e9b0c577fc728d9393e2`. Целостность SQLite — `ok`.
- Весь `ttwr.cfg`, сохранённый при закрытии исходной версии, совпал побайтно при старте 0.1.8 и после её штатного закрытия. Выбранные 16 настроек также проверены в обоих работающих окнах.
- В каждой копии удалены обе старые успешные установки: всего 12 папок. Последняя папка обновления и её `backup` сохранились; появился `confirmed-start.txt` версии 0.1.8.
- В каждой последней резервной копии проверены все 25 резервируемых файлов исходной программы по оригинальному ZIP. Исходный `checksums.json` сохранён без изменения, в том числе полный манифест со ссылками на Java.
- Неудачная, незавершённая и неизвестная папки, посторонние заметки и архив устаревшего документа сохранились.
- Встроенная `runtime` не изменилась по хешу всех файлов. В варианте с системной Java она не появилась; Java x32 сохранилась.
- Контрольные файлы в `Tours` и `Backup` не изменились. Все 25 файлов установленного образа 0.1.8 сверены по его манифесту.
- Старый и новый процессы Java завершились с кодом 0; после закрытия WAL/SHM отсутствуют.

Начальная геометрия искусственного профиля могла адаптироваться к экрану при первом старте старой версии. Побайтное сравнение настройки обновления начинается с её штатного сохранения исходной программой.
