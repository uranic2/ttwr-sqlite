# BL-04 и BL-07: реализация и проверки — 14 ноября 2026 года

Изменения включены в версию 0.1.7. Описанные ниже замеры и локальные проверки выполнены на рабочей сборке до повышения номера версии; при выпуске GitHub Actions повторяет полный набор проверок. Исходная версия 0.1.6 и её ZIP не заменяются.

## BL-04: импорт Players.xml

- `StreamingPlayers` разбирает XML за один SAX-проход. Поля читаются напрямую, DOM не создаётся. При обычной загрузке HTTPS промежуточный XML больше не записывается и не перечитывается.
- Сохранены правила исходного `Player.LoadXML`: первые подходящие поля и значения первых дочерних узлов, CDATA, комментарии, инструкции обработки, дубли и вложенные игроки, Unicode, статистика и отрицательный ноль. Для обычных отдельных записей память ограничена текущим игроком; необычные вложенные `Player` буферизуются до закрытия внешнего игрока, чтобы сохранить исходный порядок обработки.
- Импорт идёт в отдельную SQLite-базу одной транзакцией. Восемь вторичных индексов строятся после записей. Схема остаётся версии 2; миграция рабочей базы не нужна.
- Перед продвижением проверяется целостность. Ошибка в конце XML, неправильный ID, отмена или прерывание не заменяют рабочую базу. Временные файлы закрываются и удаляются.
- Прогресс во время чтения показывается по байтам; при неизвестной длине не выдумывается общее количество игроков. Итоговое число передаётся после разбора, затем отдельно обозначается построение индексов. При явном запросе XML-кеша сохраняется прежний контракт копирования исходных байтов.

## Сравнительные замеры

Синтетический XML: **150 000 игроков**, 61821795 байт. Windows x64, Oracle JDK 25.0.1 x64, `-Xmx512m`, локальный диск. Исходная реализация взята из опубликованного ZIP 0.1.6, новая — из текущей сборки. Для каждого запуска создавалась отдельная БД. Порядок: исходная, новая, новая, исходная.

| Показатель | Исходная 0.1.6 | Новая реализация |
|---|---:|---:|
| Импорт, запуск 1 | 11,738 с | 7,426 с |
| Импорт, запуск 2 | 12,287 с | 7,542 с |
| Среднее время | 12,013 с | 7,484 с |
| Байты чтения процесса | 5 943 050 853 | 4 832 310 115 |
| Байты записи процесса | 1 489 647 033 | 235 361 764 |
| Итоговая SQLite-база | 94 838 784 байта | 89 706 496 байт |
| Наблюдаемый пик Java-кучи | 306,35–306,40 МиБ | 305,17–306,23 МиБ |

Время уменьшилось примерно на **38%**, объём записи процесса — на **84%**. Заметного снижения пика кучи эти прогоны не показали. Отказ от DOM не следует представлять как подтверждённое снижение пикового потребления памяти в этих условиях.

Во всех четырёх результатах по 150 000 игроков, целостность `ok`, все столбцы таблицы `players` совпали. SHA-256 логического содержимого: `096d6e7ee18cd7437ea109c22a8081265035e73cd99f5223033a538218d7f027`.

Методика: `ttr.ImportBenchmark` измеряет время импорта и опрашивает используемую Java-кучу каждые 10 мс. Время не включает последующий контрольный обход записей. Счётчики `GetProcessIoCounters` сняты для всего дочернего процесса после завершения; они включают ввод-вывод через файловый кеш и **не равны физическим операциям накопителя**. Это два прогона каждого варианта на одной машине, без гарантии холодного файлового кеша; результаты не являются обещанием такой же скорости на другом компьютере или реальной базе.

Исходные результаты и синтетические базы: `.local/bl04-benchmark-9645dbe518f04d599d28c5df57923cc4/results.json`. Для воспроизведения сравнения нужно сохранить оригинальный ZIP 0.1.6 и запускать один и тот же `ttr.ImportBenchmark` на обоих архивах с одинаковым XML и новой выходной БД.

## BL-07: хранение обновлений

`UpdateStorage` вызывается в фоне после открытия главного окна. Очистка начинается только при совпадении файлов установленной программы с проверенным образом соответствующего обновления и наличии полностью проверенной резервной копии.

Сохраняется последняя подходящая папка обновления целиком: исходный ZIP, распакованный образ, помощник, журнал и `backup`. Более старые распознанные успешные установки удаляются после повторной проверки. Незавершённые, неудачные, неизвестные, повреждённые и содержащие посторонние файлы папки остаются. Если последнюю пригодную копию подтвердить нельзя, старые копии не очищаются.

Проверяются допустимые имена файлов, манифесты и SHA-256 обоих образов, границы каталогов и отсутствие ссылок/junction. Пользовательская `data`, БД, WAL/SHM, настройки, турниры, Java и архив `retired-files` не входят в очищаемые деревья. При ошибке удаления последняя копия сохраняется; остатки старой папки могут потребовать отдельного разбора.

Пункт **«Справка → Файлы обновлений…»** показывает объём доступных файлов `data/updates` и расположение последней подтверждённой резервной копии. Внешние связанные деревья при подсчёте не обходятся.

## Проверки

- Сравнение SAX-результата с оригинальным DOM-декодером по всем столбцам, ошибка в конце XML, некорректный ID, внешние сущности, отмена, прерывание, наличие всех индексов.
- Политика хранения: две старые успешные установки удаляются, последняя копия сохраняется; неудачные, незавершённые, неизвестные и повреждённые папки, профиль, Java и внешние ссылки остаются. Проверены объём и повторный запуск.
- Настоящий старт окна подтверждает автоматический вызов очистки и пункт просмотра объёма.
- Полный набор SQLite, переносимого профиля, обновления, закрытия и GUI-проверок; отдельный установщик с ожиданием блокировки и перезапуском native-помощника.

Полный набор с GUI и native-перезапуском прошёл на Java 25.0.1 x64 и Temurin 8u472 x32 на текущей Windows x64. Символические ссылки без привилегий доступны не во всех средах; защита новых деревьев обновлений дополнительно проверяется на Windows junction.

Проверки выполняются только на новых синтетических профилях. Рабочая папка программы и данные пользователя не использовались. Команды и режимы — в [Тестирование.md](../Тестирование.md).
