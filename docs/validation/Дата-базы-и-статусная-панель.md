# Дата базы TTWR и статусная панель — 15 ноября 2026 года

Исследование и исправление выполнены на исходниках **0.1.10**. Исправление пока не опубликовано; VERSION не повышался. Пользовательская рабочая база не изменялась.

## Что делал оригинальный TTWR

Проверен байткод исходного vendor/upstream/ttwr.dat, SHA-256 совпал с config/dependencies.lock.json. Использованы DBMain.LoadXML/SaveXML, Updater.GetDBLastUpdatedData, Updater$1.run, DBUpdateDlg$9.run, TTRClient.UpdateDB и TTRClient$24.OnCompleteDBCheck.

| Операция | Поведение оригинала |
|---|---|
| Чтение установленной даты | Атрибут DB/@date локального DB/db.xml → DBMain.date |
| Формат | d.M.yyyy-H:m:s |
| Источник серверной даты | Первая строка ../db_last_updated.php относительно адреса db.xml |
| Резервный источник | DB/@date серверного db.xml, если сервис не дал строку даты |
| Сравнение | Calendar.compareTo: вся дата со временем; обновление доступно при строго более новой серверной дате либо неизвестной локальной |
| После успешной загрузки | DBUpdateDlg$9 повторно получает дату публикации и присваивает её новому DBMain.date, если она известна |
| Сохранение | DBMain.SaveXML записывает эту дату в локальный db.xml |
| Повторная проверка | TTRClient.UpdateDB после успешного сохранения вызывает updater.CheckForUpdateDB |
| Панель jStatusDB | Показывает локальную дату dd.MM.yyyy; question.png при недоступной проверке, warning.png при более новой базе, ok.png при актуальной |

Дата каталога не является временем выполнения обновления и не берётся из даты файла Players.xml/Players.sqlite. Схема статуса оригинала использована и для SQLite-каталога.

## Подтверждение причины

15 ноября 2026 года сначала выполнены два небольших HTTPS-запроса к публичному серверу. Позже по отдельному запросу пользователя полностью прочитан Players.xml потоковым просмотром тегов, атрибутов и искомых строк; рабочая база при этом не изменялась.

| Проверенный адрес | Ответ |
|---|---|
| [db.xml](https://ttw.ru/ttw-r/db/db.xml) | DB/@date = **06.10.2026-23:23:57** |
| [db_last_updated.php](https://ttw.ru/ttw-r/db_last_updated.php) | **15.11.2026-03:23:50** |

Оба запроса вернули HTTP 200. У db.xml был Last-Modified 14 ноября 2026 года, но он также не является датой каталога.

В 0.1.10 при замене штатного обновления на PlayersUpdateSession/новое DBUpdateDlg были пропущены перенос даты публикации после загрузки и обновление статусной панели. В подготовленный локальный db.xml попадала старая дата серверного заголовка — 06.10.2026. При сравнении с 15.11.2026 сервис правдоподобно сообщал о более новой базе, хотя записи только что скачались. Дополнительно панель могла оставаться с прежней датой/значком до очередной фоновой проверки.

## Исправление

- DatabaseDate получает дату публикации с явными таймаутами 15 секунд и поддержкой отмены. При ошибке или неверном ответе после загрузки используется дата уже полученного заголовка, без повторного чтения Players.xml или db.xml. Если обе даты неизвестны, новая дата не выдумывается.
- PlayersUpdateSession после успешного чтения всех компонентов получает дату публикации и сохраняет её в подготовленном db.xml **до применения комплекта**. При отмене, ошибке импорта или откате прежний заголовок и DBMain.date остаются прежними.
- Локальный импорт профиля сохраняет дату источника. Серверная дата не подставляется локальному каталогу.
- DatabaseStatus обновляет оригинальный обработчик jStatusDB в потоке Swing после применения и обновления таблицы. Старые сетевые ответы отсеиваются по поколению проверки. Текущая установленная дата читается при обработке результата, а не захватывается перед сетевым ожиданием.
- BuildSqliteTTWR направляет Updater.CheckForUpdateDB в этот обработчик. Исходный callback TTRClient$24 продолжает выбирать штатные значки и текст подсказок; старый обновлятор самой программы остаётся отключённым.
- DBMain использует общий разбор даты. Неверный/отсутствующий атрибут не оставляет дату от ранее прочитанного заголовка.

Схема SQLite не изменена: совместимым хранилищем метаданных каталога остаётся **data/DB/db.xml**, а Players.sqlite хранит игроков. Время компьютера, Last-Modified и файловые timestamp вместо даты публикации не используются.

## Ограничения и применение

- Реальный сервер использован для чтения db.xml, даты публикации и отдельного исследования Players.xml. Импорт реального списка в рабочую базу не выполнялся: автоматические проверки используют синтетические данные и имитацию HTTPS.
- Это исправление исходников, а не изменение уже установленного ZIP 0.1.10. Для существующей установки нужна исправленная сборка и одно повторное штатное обновление списка. Старая дата не меняется автоматически на текущую без загрузки каталога.
- Java x32 проверена на Windows x64, отдельная 32-разрядная Windows не проверялась.
- Необязательная проверка символьной ссылки RetiredFilesChecks в x32-прогоне была пропущена из-за прав/платформы; проверки junction при импорте и проверки актуальности дат прошли.
- Ответы сервера не образуют версионированный атомарный снимок. Как в оригинале, используется дата публикации, полученная после загрузки; при обновлении файлов самим сервером посреди операции отдельной серверной гарантии согласованного снимка нет.

См. [оригинальную архитектуру](../Архитектура-оригинального-TTWR.md), [архитектуру SQLite-версии](../Архитектура.md) и [инструкцию пользователя](../Руководство-пользователя.md).
