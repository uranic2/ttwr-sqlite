# TTWR: переход каталога игроков на SQLite

Дата: 10 ноября 2026 года.

## Статус версии

SQLite-версия собрана и проверена отдельно от установленной программы. На момент сохранения установленная программа в `Program Files` ещё использует исправленный XML-вариант; она не заменялась. Для переноса подготовлен новый запускатель **`ttwr-sqlite.exe`**. Полный комплект включает Java Temurin 25.0.5 x64; при отсутствии подходящей `runtime` используется внешняя Java 8+ x64 или x32. Изменения Java-программы находятся в `app/ttwr.dat`, зависимости — в `app/lib`.

**Переносимый комплект содержит минимальную стартовую БД: 0 игроков и отсутствие даты обновления.** При первом запуске создаётся папка **`data` рядом с `ttwr-sqlite.exe`**, затем каталог заполняется через «База данных → Обновить базу данных». Профиль `%APPDATA%\TTWR` старой программы не используется и не импортируется автоматически. Вся папка комплекта переносится целиком; системная Java и настройка PATH для нового запускателя не нужны.

В `data` находятся `ttwr.cfg`, дополнительные данные `ttwr_data.xml`, журналы, каталог `DB`, турниры `Tours`, резервные копии `Backup` и экспорт `stats`. При переносе папки основные пути настроек привязываются к новому расположению. Если локальная папка недоступна для записи, запуск сообщает об ошибке и не переходит на AppData.

В исходном XML — **149 194 игрока**. Все они перенесены в SQLite. Исходный `Players.xml` оставлен без изменений. Это снимок на момент миграции, а не файл, который SQLite-версия будет обновлять при обычном сохранении.

## Что изменилось в работе программы

- Основной каталог игроков хранится в `Players.sqlite`. Получение игрока по ID, поиск, фильтрация, сортировка и страницы списка выполняются запросами к SQLite.
- Полный каталог больше не загружается в постоянную `HashMap`. Слабые ссылки сохраняют идентичность ещё используемых объектов, не удерживая весь каталог в памяти.
- Таблица показывает страницы по 100 игроков. Поиск выполняется с небольшой задержкой после ввода, в фоновом задании. Сортировка применяется ко всему результату запроса.
- Подтверждённые изменения игроков записываются в БД сразу. Связанные операции объединяются в транзакции; ошибка или отрицательный результат отменяют такую операцию. Нажатие «Нет» в последующем общем вопросе о сохранении базы не отменяет уже записанные изменения игроков. Тексты вопросов уточнены.
- При подтверждённом выходе явно закрываются все открытые SQLite-хранилища. Дополнительно зарегистрирован обработчик завершения Java. Отмена выхода оставляет подключения открытыми. После закрытия последнего подключения SQLite сам убирает WAL/SHM.
- Обычный `DBPlayers.SaveXML()` больше не создаёт DOM каталога и не переписывает `Players.xml`: он завершает сохранение SQLite либо создаёт копию SQLite для другого пути.
- Если SQLite уже существует, он является источником данных. Изменение старого XML не вызывает автоматического повторного импорта. XML используется для первоначального импорта и обмена.
- Форматы турниров, регионов, шаблонов, файлов рейтингов и метаданных базы целиком не переводились на SQLite. Обмен XML с сервером и экспорт игроков турнира сохранены. Рейтинговые данные на дату подготавливаются как отдельные области SQLite и затем выбираются запросами.

## Как обновляется каталог с рейтингами игроков

Здесь под каталогом с рейтингами понимается общий список игроков: раньше локальный `Players.xml`, в подготовленной версии — `Players.sqlite`. Отдельные рейтинговые списки турниров рассмотрены ниже.

### Проверка обновления с сервера

1. `Updater.GetDBLastUpdatedData()` запрашивает дату публикации через `../db_last_updated.php` относительно адреса базы, встроенного в программу. Если этот запрос не дал строку даты, программа пытается прочитать атрибут `date` серверного `db.xml`.
2. Дата разбирается в формате `d.M.yyyy-H:m:s` и сравнивается с датой открытой базы `DBMain.date`. Если серверная дата новее либо локальная дата неизвестна, обновление считается доступным. Это проверка даты публикации, а не сравнение рейтинга каждого игрока или контрольных сумм файлов.
3. Окно `DBUpdateDlg` читает серверный `db.xml`. Имя XML-файла игроков берётся из `PlayerDB/@name`, а не задаётся в коде как обязательное `Players.xml`. Названия остальных файлов также описаны в заголовке базы.

### Загрузка и применение новой базы

1. Обновление проверяет открытые неучтённые турниры и необходимость сохранить изменения. PlayersUpdateSession создаёт отдельный подготовленный комплект.
2. Серверный db.xml задаёт имена XML игроков, регионов и шаблонов. Игроки читаются одним SAX-проходом непосредственно во временную SQLite-базу; затем создаются индексы и проверяется целостность.
3. После успешного чтения получается дата публикации из db_last_updated.php. Она записывается в candidate.date и подготовленный db.xml; при недоступной/неверной дате используется дата уже полученного заголовка. Время скачивания и Last-Modified вместо даты каталога не подставляются. Этот шаг, присутствовавший в оригинале, восстанавливается исправлением после 0.1.10.
4. DbPackageTransaction резервирует прежний DB, заменяет четыре проверенных файла с журналом восстановления и переключает активный каталог. При обычной ошибке предпринимается откат; незавершённое применение восстанавливается при старте.
5. После применения и обновления страницы таблицы статусная панель получает новую локальную дату и результат сравнения. Запоздавшие ответы старых проверок игнорируются. При локальном импорте сохраняется дата источника, а свежесть проверяется отдельно.
6. Отмена либо ошибка до применения оставляет прежние файлы и дату. Подробные проверки: [дата базы и статус](validation/Дата-базы-и-статусная-панель.md).

**Обновление получает полный серверный каталог, а не набор изменений отдельных рейтингов. Автоматического слияния с локальными исправлениями игроков здесь нет.**
После перехода обычное серверное обновление не должно переписывать прежний локальный `Players.xml`: рабочим результатом служит `Players.sqlite`. Обновление даты базы сохраняется в `db.xml`. Старый XML остаётся снимком прежнего состояния, пока пользователь явно не выполнит экспорт.

### Локальные расчёты рейтинга и отдельные рейтинговые списки

Изменение рейтинга через программу записывается в SQLite механизмом отслеживания полей. В частности, исходный `RatingList.ApplyToPlayersDB()` переносит в основной каталог рейтинг `Rating + deltaR`, обнуляет перенесённую прибавку и складывает основную и дополнительную статистику турниров, побед и поражений. В подготовленной версии эти записи выполняются в транзакции.

Рейтинговые списки турниров сохраняют прежний механизм работы с XML и имена вида `RLists/YYYYMMDD.xml`; это отдельный формат, не синоним общего `Players.xml`. Для получения рейтинга на дату `DBPlayers` подготавливает из объектов `RatingList` области `scope` вида `rating:…` в таблице SQLite. После изменения списка подготовленная выборка признаётся устаревшей и строится заново при следующем обращении. Это не скачивание всего серверного каталога.

## Как формируется файл SQLite

Файл называется **`Players.sqlite`**. Это двоичная база SQLite, содержащая таблицы, индексы и данные. Текстовый дамп с командами и расширением `.sql` при обычной работе не создаётся. SQL-команды программа выполняет напрямую через JDBC-драйвер.

### Первоначальное преобразование XML

1. При загрузке локального XML определяется соседний файл с тем же основным именем и расширением `.sqlite`: например, `Players.xml` → `Players.sqlite`. Если SQLite уже существует, открывается он, а XML повторно не импортируется. Проверяются версия схемы, обязательные поля и целостность. Если явно запрошен отсутствующий файл `.sqlite`, загрузка возвращает ошибку.
2. Если SQLite ещё нет, `SqlitePlayersIntegration.importXml()` создаёт в целевой папке промежуточный файл `.ttwr-import-….sqlite`. `SqlitePlayersStore` открывает его и создаёт схему версии 2, таблицы `players` и `metadata`, а также восемь индексов. Данные основного каталога получают `scope='current'`; ключ записи — `(scope, id)`.
3. Начинается транзакция импорта. `StreamingPlayers.loadInto()` выполняет один SAX-проход и читает поля без DOM. Для обычного HTTPS-импорта не создаётся промежуточный XML. Вторичные индексы строятся после записей; проверяется весь документ и целостность временной SQLite-базы. При явном запросе XML-кеша сохраняются исходные байты.
4. SAX-обработчик напрямую формирует игрока с сохранением правил прежнего `Player.LoadXML()`. Адаптер `SqlitePlayerMap` передаёт игрока в подготовленный запрос `INSERT OR REPLACE`. В SQLite записываются профиль, рейтинг, места, флаги, обе группы статистики и служебные ключи поиска. Полный DOM XML и постоянная карта всех игроков не создаются.
5. Успешный импорт фиксируется, затем выполняются `PRAGMA integrity_check` и checkpoint журнала. Хранилище закрывается. Промежуточный файл перемещается на целевой путь; используется атомарное перемещение, если его поддерживает файловая система. После этого база открывается для работы. При ошибке импорта выполняется откат и удаляются промежуточные файлы.

Для сохранённой версии отдельно подготовлен файл `Сборка/migration/Players-final.sqlite`: 149 194 игрока, проверенная схема версии 2 и все индексы. Его содержимое сверено с исходным XML, а полный обратный экспорт прочитан прежней программой. Само копирование этого файла в папку снимка не устанавливает его в рабочий профиль.

### Последующие изменения и сохранение

Изменённые поля записываются через `UPDATE`, новые игроки — через вставку, удаление — через `DELETE`. Для этого не требуется заново формировать весь файл из XML. SQLite самостоятельно обновляет страницы базы и служебный журнал.

Используется режим WAL. Рядом с открытой базой могут находиться `Players.sqlite-wal` и `Players.sqlite-shm`. Подтверждённые изменения могут ещё находиться в WAL, поэтому копия одного основного файла открытой базы не обязательно содержит последние данные. `DBPlayers.SaveXML()` вызывает SQLite-сохранение: для текущего пути выполняется checkpoint, для другого пути — SQLite Backup API. При новом целевом пути резервная копия сначала формируется во временном файле.

Явный экспорт в прежний XML выполняется утилитой `ttr.SqliteCatalogTool export <SQLite> <XML>`. Это отдельная операция для обмена или возврата к XML-версии; обычное сохранение её не вызывает.

## Установка, зависимости и Java

В полном переносимом комплекте Java уже включена: Eclipse Temurin 25.0.5 x64, полный JRE с файлами лицензий. Папка `app` обязательна; `runtime` необязательна при наличии внешней Java 8+. Native-запускатель заменён с `jpackage` на собственный x86 EXE, запускающий Java отдельным процессом. Он не загружает JVM внутрь себя и поэтому поддерживает обе разрядности Java. Дополнительные .NET и компиляторы пользователю не нужны. SQLite работает внутри процесса Java. Отдельная установка SQLite, отдельный сервер БД, системный ODBC-драйвер или настройка DSN не требуются.

Порядок поиска: `runtime/bin/java.exe`, `JAVA_HOME`, `JRE_HOME`, `java.exe` в PATH, затем реестр текущего пользователя и компьютера в 64- и 32-разрядном представлениях. Проверяются JavaSoft, Eclipse Adoptium, AdoptOpenJDK, Microsoft JDK и Zulu. Каждый существующий кандидат сначала запускается с `-XshowSettings:properties -version`: требуются успешный выход, Java 8+ и определимая разрядность 32/64. Неподходящий кандидат пропускается. Это не выбор самой новой версии среди всех установленных: при необходимости явный выбор задаётся через `JAVA_HOME`.

Для x32 передаются `-Xms64m -Xmx512m`, для x64 — `-Xms64m -Xmx1024m`. Флаг `--enable-native-access=ALL-UNNAMED` передаётся только начиная с Java 24; Java 8 его не получает. Путь данных в обоих случаях остаётся локальным `<каталог EXE>/data`. При отсутствии подходящей Java показывается ошибка. Выбор и завершение Java записываются в `data/launcher.log`, stdout/stderr запуска — в `data/launcher-java.log`. На уровне первоначальных настроек `PortableStart` также указывает 512 МБ для нового профиля x32.

Комплекты: `TTWR-SQLite-Windows-x64.zip` содержит Java x64, а `TTWR-SQLite-system-Java.zip` содержит то же приложение и стартовую БД без `runtime`. Поддержка Java x32 проверена на Windows x64; отдельная 32-разрядная Windows не проверялась. Прежний `app/ttwr-sqlite.cfg` относился к запускателю jpackage и в новом комплекте не используется.

Прежний запускатель `ttwr.exe` вызывал `javaw.exe` с `-jar ttwr.dat`; это могло давать внешне незаметный отказ на компьютере без Java в PATH или без соседнего архива программы. Точная причина отказа на другом компьютере по одному отсутствию окна не установлена. Для проверки встроенной Java используется `runtime\bin\java.exe -version`; команда `java -version` относится к системной установке и для новой сборки не обязательна.

**JDBC-драйвер SQLite нужен и уже включён** в `lib/sqlite-jdbc-3.54.1.0.jar`. Он содержит Java-часть и native-библиотеки SQLite, в том числе для Windows x86 и x86-64. При запуске драйвер выбирает библиотеку под архитектуру Java. Для её загрузки требуется доступная для записи временная папка, а для рабочей базы и WAL — права записи в папку данных.

В сборку также включены `slf4j-api-1.7.36.jar` и `slf4j-nop-1.7.36.jar`, а также прежние библиотеки `activation-1.1.1.jar`, `commons-net-3.6.jar`, `javax.mail.jar`. Их не нужно устанавливать по отдельности: при переносе программы следует сохранять всю папку `lib`.

**Программа работает на Java 25: подготовленная сборка проверена на Java 25.0.1 x64 в Windows.** Проверены SQLite-операции и запуск через обычный `ttwr.exe` в отдельном профиле. Интеграционные проверки также прошли на Java 8u321. Это подтверждение проведённых проверок, а не гарантия каждого сценария старой программы.

На 10 ноября 2026 года [Oracle указывает Java 27 как последнюю версию, а Java 25 как последнюю LTS-версию](https://www.oracle.com/java/technologies/downloads/). Java 27 этой сборкой пока не проверялась. Для подтверждённого запуска можно использовать Java 25 x64.

В манифест `ttwr.dat` добавлено `Enable-Native-Access: ALL-UNNAMED` для запуска через `java -jar`. При ручном запуске через `java -cp` на Java 25 используется параметр `--enable-native-access=ALL-UNNAMED`; это относится к загрузке native-библиотеки JDBC-драйвера. Отдельного системного драйвера такая настройка не устанавливает.

## Изменения по классам

### `ttr.DBPlayers`

Заменён слой доступа к каталогу с сохранением интерфейса, необходимого остальной программе. Поле `players` теперь содержит совместимый адаптер `SqlitePlayerMap`. Получение игрока выполняет SQL-запрос. Списки местоположений строятся запросами уникальных значений. Поиск похожих игроков использует индекс фамилий. Места рассчитываются в SQL с учётом равных рейтингов.

Добавлен постраничный запрос с фильтрами и сортировкой, включая рейтинг на выбранную дату. Старые имена методов загрузки и сохранения оставлены для совместимости, но обычная работа этих методов направлена в SQLite. При сохранении в другую папку отслеживание живых объектов переносится на новое хранилище.

Старый `GetArray()` остаётся совместимым методом и способен материализовать каталог, если его явно вызвать. Новый список игроков и экспорт игроков турнира его для полного каталога не вызывают.

### `ttr.SqlitePlayersStore` — новый класс

Репозиторий JDBC. Таблица `players` имеет составной первичный ключ `(scope, id)` и хранит профиль, рейтинг, места, признаки изменений и обе группы статистики. Область `current` содержит основной каталог; дополнительные области обслуживают исторические рейтинги. Версия схемы — 2.

Добавлены индексы имени, фамилии, рейтинга, региона, города и значений справочников. Фильтры передаются параметрами запросов. Для поиска подготовлены Unicode-ключи; отдельно учтены правила сравнения фамилий, включая варианты буквы I. Два служебных признака сохраняют различие `0.0` и `-0.0`, обнаруженное при полном сравнении исходных данных.

Настроены WAL, `synchronous=FULL` и ожидание занятой базы. Перед использованием существующей БД проверяются версия и обязательные столбцы. Полная проверка целостности используется при миграции и в проверочной утилите; обычное открытие использует быструю проверку.

Копии создаются через SQLite Backup API. Простое копирование открытого файла SQLite с возможным журналом WAL для сохранения не используется. Для нового целевого пути применяется промежуточный файл с последующим перемещением.

### `ttr.SqlitePlayerMap` — новый класс

Адаптер `Map` позволяет старому коду обращаться к SQLite через прежнее поле `players`. Размер, наличие ID, чтение, добавление и удаление выполняются через репозиторий. Итератор получает ID порциями по 256, а не создаёт сразу массив всех игроков.

### `ttr.SqliteMutations` и `ttr.SqliteFieldSetters` — новые классы

В старой программе поля игроков, профилей и статистики открыты и часто изменяются прямым присваиванием. Изменённый байткод направляет такие записи через вспомогательные методы: поле меняется, затем соответствующее значение сохраняется в SQLite.

Связи объектов с хранилищем используют слабые ссылки. При замене объекта профиля или статистики прежняя связь снимается. Границы составных операций обеспечивают фиксацию либо откат транзакции; после отката обновляется состояние используемых объектов. Изменения рейтингового списка сбрасывают подготовленные исторические выборки.

### `ttr.SqlitePlayersIntegration` — новый класс

Связывает старые точки загрузки и сохранения с SQLite. Существующая локальная SQLite-база имеет приоритет, даже если исходного XML уже нет. Первоначальный импорт выполняется потоковым XML-загрузчиком в транзакции во временную SQLite-базу. Только успешный импорт с проверкой целостности продвигается на целевой путь.

Загрузка XML по HTTPS использует отдельную временную SQLite-базу. Отмена и ошибка не подменяют действующий каталог. Экспорт для турнира выбирает новые и изменённые записи и список новых игроков данного турнира, не выгружая весь основной каталог в массив.

### `ttr.DBMain`

Изменена последовательность сохранения: сначала данные, затем метаданные. Ошибки сохранения учитываются. При смене пути каталог подключается по новому адресу с сохранением отслеживания объектов. Исправлен повторный подбор свободного ID: признак допустимости сбрасывается для каждой попытки. Метаданные `db.xml` остаются XML, но запись `PlayerDB` указывает на SQLite.

### `ttr.UI.PlayersListPanel`

Переписан список игроков при сохранении внешнего интерфейса панели. Добавлены страницы по 100 записей, переходы между страницами, общее количество найденных игроков и SQL-сортировка столбцов со стрелкой направления. Поиск запускается через 180 мс после ввода, запросы выполняются через `SwingWorker`.

Фильтры имени, региона и города применяются совместно. Сохранены сценарии выбора игрока, Enter, двойной щелчок, добавление, изменение, удаление, просмотр профиля и списка турниров. В режиме выбора доступны соответствующие этому режиму действия. Прежние внутренние классы панели удалены из архива.

### `ttr.SqliteUpdates` — новый класс; `ttr.TTRClient`

В обновление базы встроены начало, успешное завершение и аварийное завершение SQLite-операции. Запоминается исходная активная база. При отмене восстанавливается исходное состояние и удаляются временные SQLite-файлы. При успешном переключении закрывается прежнее хранилище. Уточнены вопросы о сохранении: игроки уже записаны, остальные данные сохраняются отдельно.

### `ttr.PortableStart` — первый запуск переносимого комплекта

Основной класс нового запускателя. Работает с `data/ttwr.cfg` рядом с EXE и создаёт локальные папки `DB`, `Tours`, `Backup`, `stats`. Если настройки отсутствуют, а `DB/db.xml` отсутствует и целевые файлы не заняты существующей базой, копирует из `app/seed` пустую БД, минимальные XML регионов и шаблонов и заголовок без даты. Полный старый каталог игроков в переносимый комплект не включается. Профиль из AppData не читается для первоначальной подготовки.

Если локальные настройки уже есть, сохраняются их параметры; основные пути пересчитываются при загрузке для текущей папки программы. Существующий локальный `db.xml` не заменяется. Если обнаружены отдельные файлы БД без заголовка, первоначальная подготовка прекращается с сообщением, а данные не перезаписываются. Копирование стартовой базы не является общим механизмом восстановления повреждённого профиля.

Первоначальные настройки отключают второй экран и автоматическое предложение обновления; пользователь запускает обновление базы из меню. Параметры памяти и native access выбираются запускателем с учётом версии и разрядности Java. Пути `ttwr.seed` и `ttwr.home` задаются относительно EXE, поэтому запуск из другого рабочего каталога поддерживается. Ошибки первоначальной подготовки выводятся в окно и `data/ttwr-sqlite-startup.log`; журнал программы — `data/ttwr.err`.

### `src/launcher/ttwr-sqlite.c` — запускатель с внешней Java

Native Windows GUI EXE собран для x86 с помощью Zig C compiler; архитектура bootstrap не ограничивает архитектуру дочернего процесса Java. Для запуска используются Unicode WinAPI и экранирование аргументов Windows, включая пробелы и обратные слеши. Оболочка командной строки для запуска Java не используется. Версия и разрядность проверяются отдельным коротким процессом с тайм-аутом, после чего выбранная Java запускает `ttr.PortableStart` с локальными путями и classpath `app/ttwr.dat;app/lib/*`.

Приоритет встроенной среды сохранён. Если её EXE отсутствует либо не запускается, проверяются внешние кандидаты. Чтение реестра не изменяет его. Настройки и данные старого TTWR не используются. Исходник запускателя и воспроизводимая команда компиляции сохранены в `src/main/native`, версия и контрольная сумма компилятора — в `config/native-toolchain.json`. Компилятор нужен только для пересборки EXE.

### `ttr.PortablePaths`; изменения `TTRClient`, `Settings` и `StreamingPlayers`

Новый `PortablePaths` определяет каталог EXE по `ttwr.home=$APPDIR/..`; для прямого запуска классов из `app/ttwr.dat` предусмотрено определение того же пути по расположению архива. Постоянный профиль — `<каталог EXE>/data`. Поиск прежних настроек через AppData не выполняется.

При сборке старые обращения `System.getenv("APPDATA")` в `TTRClient` и совместимом XML-загрузчике направляются через `PortablePaths.getenv`, а добавляемый суффикс `\\TTWR\\` меняется на `\\data\\`. Это охватывает статические пути настроек, метаданных, журналов, CSV статистики и старого XML-кэша. Переменная окружения Windows и файлы старого TTWR не изменяются. Остальные переменные окружения читаются как прежде.

В `Settings.Load()` добавлена обработка успешной загрузки через `PortablePaths.afterLoad`: база открывается из `data/DB/db.xml`, турниры — из `data/Tours`, резервные копии — из `data/Backup`. Каталог списка турниров и настроенный каталог архивов также получают локальные пути. Ссылки на открытые турниры переносятся относительно прежней папки турниров; внешняя абсолютная ссылка автоматически не направляет программу обратно в старый профиль. Остальные параметры сохраняются. Это позволяет переносить всю папку программы вместе с `data` без обращения к прежнему абсолютному адресу.

### `ttr.SqliteCatalogTool` — новая утилита

Команды `import`, `export`, `check` позволяют отдельно импортировать XML, экспортировать актуальную SQLite-базу в прежний XML и проверять целостность. Полный экспорт проверен повторным чтением старой XML-версией программы.

### `ttr.SqliteLifecycle` — новый класс; закрытие программы

Добавлен при исправлении выхода 10 ноября 2026 года. Реестр открытых хранилищ закрывает все подключения при подтверждённом закрытии главного окна. В `TTRClient.formWindowClosing()` добавлен вызов после прежних операций сохранения; проверяется итоговый режим закрытия окна. Если пользователь отменил выход или сохранение завершилось ошибкой, подключение остаётся открытым.

Резервный JVM shutdown hook закрывает оставшиеся хранилища при обычном завершении Java, в том числе через `System.exit()`. Ошибка одного хранилища не мешает попытке закрыть остальные. При ошибке обычного выхода окно не закрывается и показывается сообщение. Аварийное уничтожение процесса, отключение питания и `Runtime.halt()` не гарантируют выполнения обработчика.

`SqlitePlayersStore` регистрируется после успешного создания. Его `close()` стал повторно безопасным: незавершённая транзакция откатывается, подготовленный запрос закрывается, затем закрывается JDBC-подключение. Закрытие подключения предпринимается даже при ошибке предыдущей очистки. Успешно закрытое хранилище снимается с регистрации. Подтверждённые транзакции при этом сохраняются.

WAL/SHM постоянной базы код вручную не удаляет: SQLite выполняет завершающую обработку при закрытии последнего подключения. Если база всё ещё открыта другой программой, служебные файлы могут оставаться до закрытия и этого подключения. Существующий код удаления собственных временных баз обновления сохранён.

### `BuildSqliteTTWR` — инструмент сборки

Собирает архив программы из сохранённого исходного варианта, заменяет классы доступа и панели, меняет записи полей и добавляет необходимые точки управления транзакциями и обновлением. Тестовые классы в рабочую программу не включаются. Собранные классы совместимы с Java 8. В манифест добавлены зависимости и разрешение native access для Java 25.

Прежние `StreamingPlayers`, `StreamingPlayerWriter` и `LoadPerformanceFix` сохранены для импорта, экспорта и совместимости.

### Проверка переносимого комплекта со встроенной Java

Следующий абзац описывает первоначальную сборку с AppData. В актуальном ZIP она заменена вариантом с отдельной папкой `data`; результаты актуальной проверки приведены далее.

Использована Eclipse Temurin 25.0.5+8 x64 из официального [выпуска Adoptium](https://github.com/adoptium/temurin25-binaries/releases/tag/jdk-25.0.5%2B8). SHA-256 скачанного JRE проверен по метаданным Adoptium; файлы лицензий сохранены в комплекте. Native-запускатель создан штатным [jpackage](https://docs.oracle.com/en/java/javase/25/docs/specs/man/jpackage.html).

В тестовом процессе из PATH исключены все каталоги Java, JAVA_HOME не задан, APPDATA направлен в новый изолированный профиль, рабочая папка запуска отличается от папки EXE. `ttwr-sqlite.exe` успешно открыл пустой список и создал профиль со стартовым `Players.sqlite` размером 49 152 байта. Затем через обычное окно обновления с реального сервера загружен XML и сформирован каталог из **149 220 игроков**. После закрытия окна WAL/SHM отсутствовали, проверка целостности обновлённой тестовой БД дала `ok`. Стартовая база в комплекте осталась пустой.

На комплектной Temurin повторно прошли интеграционные проверки каталога и четыре сценария закрытия. Отдельно проверено, что повторный запуск не заменяет настройки и БД, восстановление отсутствующих настроек сохраняет существующий каталог, а неполный профиль не перезаписывается. Проверка проводилась на этом Windows-компьютере с изолированной средой, а не на отдельной физической машине.

Результаты сохранены в `docs/validation/portable-first-run.txt`, `portable-integration.txt`, `portable-shutdown.txt`, `portable-live-update.txt`. Полный каталог из обновления используется только в тестовом профиле; в переносимый ZIP включена только пустая стартовая база.

### Проверка локальной папки данных и изоляции от старого TTWR

### Проверка запуска с Java x32 и без runtime

Через настоящий новый EXE проверены SQLite и выбор внешней Java: `JAVA_HOME` с Java 25 x64; `JAVA_HOME`, `JRE_HOME` и PATH с Temurin Java 8u472 x32; поиск через настоящий реестр Windows с Oracle Java 8u321 x64. Отдельно проверен приоритет комплектной Temurin 25 x64 при `JAVA_HOME`, указывающем на Java x32.

Для ошибки отсутствия Java и отклонения Java 7 использована тестовая сборка того же исходника с изолированными функциями поиска PATH/реестра: проверены ненулевой код возврата и запись сообщения, без изменения системного реестра.

## Сохранённые версии

- `TTWR — версия до SQLite — 2026-11-10` — установленный XML-вариант с прежними исправлениями производительности и своим описанием.
- `TTWR — версия SQLite — 2026-11-10` — отдельный снимок подготовленной SQLite-версии, её исходников, проверок и каталога на момент миграции. Этот снимок не означает, что новая версия установлена в `Program Files`.

Новый `ttwr-sqlite.exe` использует собственную папку `data` рядом с EXE. Для переноса на другой компьютер копируется весь комплект вместе с `data`, если требуется сохранить уже загруженную базу и настройки. В распространяемом ZIP папки `data` нет: при первом запуске создаётся минимальная база. Старые пользовательские настройки из AppData автоматически не используются.
