# Инструкции для работы с TTWR SQLite

## Назначение и начало работы

Это Windows-модификация TTWR: список игроков хранится в SQLite, база и настройки — в `data` рядом с `ttwr-sqlite.exe`. Профиль оригинального TTWR в AppData остаётся независимым.

Корень проекта — каталог этого файла. Здесь находятся новые помощники и восстановленные изменённые классы, а не полный исходный проект оригинального TTWR. Остальные классы берутся из `vendor/upstream/ttwr.dat`, включённого в Git. Его SHA-256 задан в `config/dependencies.lock.json`; не подменяйте этот архив модифицированной сборкой.

Перед изменениями прочитайте [README](README.md), нужные документы в `docs/` и проверьте `git status`. Общайтесь на русском. Указывайте, что изменено, что фактически проверено и какие ограничения остались. Не включайте в коммит чужие или появившиеся параллельно изменения без связи с задачей.

Версию всегда читайте из `VERSION`; состояние релизов, тегов и локальных комплектов проверяйте заново. Старые рабочие папки, снимки и отчёты не заменяют текущие исходники и новые проверки.

## Структура проекта

- `src/main/java/ttr/` — SQLite, потоковый XML, переносимый профиль и изменённые классы программы.
- `src/main/java/ttr/updates/` — получение релизов, прогресс и отмена загрузки, установка и хранение копий обновлений.
- `src/main/native/ttwr-sqlite.c` — Windows-запускатель.
- `tools/java/` — сборка архива и преобразования байткода оригинального TTWR.
- `src/test/java/`, `src/test/native/`, `src/test/python/` — проверки Java, запускателя и политики хранения релизов.
- `scripts/` — зависимости, сборка, тестирование, упаковка, публикация и очистка старых релизов.
- `config/` — зафиксированные версии, SHA-256 и параметры инструментов.
- `docs/validation/` — сохранённые результаты с методикой и ограничениями.
- `docs/backlog/Список-задач.md` — указатель бэклога; отдельные задачи — `BL-XX. …md`, завершённые — в `docs/backlog/Сделано/`.
- `vendor/upstream/ttwr.dat` — единственный разрешённый бинарный вход сборки в Git. Остальные `vendor/`, `.cache/`, `.local/`, `build/`, `dist/`, `releases/` исключены из Git.

Редактируйте исходники и сценарии, затем пересобирайте результат. Правки только в `build` или `dist` не являются исправлением программы. Пожелания в бэклоге остаются планами до реализации и проверки; например, наличие BL-12 не означает, что программа уже поддерживает тестовый канал обновлений.

## Совместимость

- Рабочие Java-классы и тесты компилируются с `--release 8`; не используйте новые API или синтаксис в этих исходниках.
- Инструменты сборки используют Java 17+ и публичный ASM. Не возвращайте зависимость от внутренних пакетов JDK.
- Для сборки нужны Windows, PowerShell, JDK 17+ и Zig для EXE. Проверенная среда — JDK 25 и Zig 0.17.1; версии проверяйте также по конфигурации проекта.
- Программа должна запускаться на Java 8+ x32/x64. Проверены Java 8 x32 и Java 25 x64 на Windows x64; это не проверка на 32-разрядной Windows.
- Запускатель предпочитает `runtime`, затем ищет Java через JAVA_HOME, JRE_HOME, PATH и обе ветви реестра. Сохраняйте Unicode, пути с пробелами, проверки версии/разрядности и понятные сообщения об ошибках.
- Версия окна «О программе», статусной строки, архива и комплекта берётся из одной встроенной версии. Изменение `VERSION` требует пересборки Java-архива.
- Ссылка в «О программе» открывает сайт проекта системным браузером через `Desktop.browse()`. Сохраняйте обработку ошибки; отрисовка ссылки не подтверждает фактический запуск браузера.
- Не добавляйте личные абсолютные пути в код и сценарии. Примеры путей к инструментам допустимы в документации.

## SQLite, XML и пользовательские данные

- Сохраняйте SQL-поиск, фильтрацию, сортировку и страницы по 100 игроков. Не загружайте весь список для отображения таблицы.
- Поддерживайте старые обращения через `DBPlayers`, `SqlitePlayerMap` и преобразованные присваивания полей. Меняя контракт, проверяйте также `BuildSqliteTTWR`.
- Импорт `Players.xml` — один SAX-проход с прямым чтением полей без DOM; восемь вторичных индексов создаются после записей во временной БД. Сохраняйте совместимость с исходным декодером: Unicode, CDATA, первые значения полей, вложенные записи, повторные ID и отрицательный ноль.
- Рабочая БД заменяется только после полного успешного импорта и проверки целостности. Ошибка в конце XML, отмена и прерывание должны оставлять исходную базу пригодной для работы.
- Обычное сохранение работает с SQLite. Экспорт XML остаётся потоковым; допустим DOM одной записи, а не всего списка.
- Сохраняйте транзакции, откат, обновление живых объектов и разделение текущих/исторических записей по `scope`. Изменение схемы требует явной миграции и проверки существующей БД.
- Закрывайте подключения после подтверждённого выхода и через shutdown hook. Постоянные WAL/SHM вручную не удаляются: ими управляет SQLite.
- Автоматические проверки используют отдельные профили и синтетические данные. Стартовый комплект содержит 0 игроков; наполнение выполняется штатным обновлением XML. Реальный список и AppData не включаются в комплект.
- При сборке, упаковке и очистке не заменяйте и не удаляйте рабочую `data`, БД, настройки или турниры.

## Обновление программы и отмена

`ReleaseClient` получает и проверяет релиз; `DownloadStats` считает показатели; `DownloadControl` управляет отменой; `UpdateDownloadDialog` отображает их; `ProgramUpdates` связывает загрузку, очистку и подтверждённый выход. `UpdateInstaller` работает отдельным процессом, а `AppInstance` защищает установку от одновременной работы приложения.

- Сохраняйте проверку доверенных HTTPS-адресов, размера ZIP, SHA-256, манифеста, встроенной версии и допустимых путей. Запрещено заменять пользовательскую `data` и `runtime` при установке автоматического обновления.
- Показатели обновляются **раз в секунду**. Текущая скорость считается за **последние 2 секунды**, средняя — за весь сеанс загрузки. КБ — 1024 байта; время — по монотонным часам. При отсутствии данных/нулевой скорости ETA неизвестно, после получения архива показатели загрузки фиксируются.
- Кнопка «Отмена», Esc и крестик используют один механизм. Сетевое/файловое закрытие выполняется вне потока Swing. Основное окно включается после завершения фоновой работы и очистки.
- Одного `SwingWorker.cancel()` недостаточно: его обработчик может выполниться до окончания ввода-вывода. Сохраняйте защиту от отмены между возвратом фонового задания и обработкой результата интерфейсом.
- Удаляется только временная папка текущей загрузки, включая частичный ZIP и распакованный образ. Ошибка удаления должна сообщать путь оставшихся файлов. Старые резервные копии и незавершённые установки других операций не очищаются этой отменой.
- Обычная ошибка записи установщика должна предпринимать откат. Сохраняйте передачу Unicode-путей помощнику через UTF-8/Base64 и относительный путь к его архиву.
- Старый обновлятор оригинального TTWR должен оставаться отключённым; сохраняйте проверку архива `VerifySqliteArchive`.

### Локальное хранение копий обновлений

`UpdateStorage` после успешного открытия главного окна проверяет установленный образ и копии по манифестам. Последняя пригодная папка обновления сохраняется целиком; более старые распознанные успешные установки очищаются. Неизвестные, неудачные, незавершённые, повреждённые и содержащие посторонние файлы/ссылки папки остаются.

**Не проверяйте резервную копию полного комплекта как полный установочный ZIP.** Java остаётся в `runtime` исходной установки и отсутствует в `backup`, хотя исходный полный манифест ссылается на неё. Для копии используется `UpdateInstaller.verifyBackup()`: допускаются отсутствующие записи только под `runtime/`, проверяются пути и формат SHA-256, все файлы приложения остаются обязательными. Исходный манифест не переписывается. Проверка загруженного образа остаётся строгой и не допускает `runtime`.

Копия файлов программы в `data/updates/.../backup` не является копией рабочей БД. Не обещайте восстановление пользовательских данных на основании одной этой папки.

## Сборка и проверки

Команды запускаются из корня. Пути ниже — примеры:

```powershell
.\scripts\build.ps1 -JdkHome 'C:\Program Files\Java\jdk-25' -Zig 'C:\Tools\zig\zig.exe'
.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25'
.\scripts\check-public-tree.ps1
```

Если Zig есть в PATH, `-Zig` можно опустить. `-SkipNative` допустим при изменении только Java и наличии проверенного запускателя; изменения C/ICO требуют полной native-сборки.

Если `build/image/ttwr-sqlite/data` уже существует, сохраните профиль и используйте отдельную копию исходников для сборки. Не удаляйте неизвестную `data` ради обхода защиты. Для ручного просмотра готовьте отдельную копию комплекта в `dist`, чтобы запуск не превращал исходный образ в рабочий профиль.

После изменения Java или преобразований байткода выполните сборку и `test.ps1`. Для обновлятора, интерфейса загрузки, установки, совместимости или упаковки используйте доступные Java x64/x32; для интерфейса — `-Gui`, для установщика — `-RestartProbe`:

```powershell
& 'C:\Tools\zig\zig.exe' cc -target x86-windows-gnu -Os '-Wl,--subsystem,windows' src/test/native/UpdateRestartProbe.c -o build/UpdateRestartProbe.exe
if ($LASTEXITCODE -ne 0) { throw 'Restart probe compilation failed' }
.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25' -Gui -RestartProbe build/UpdateRestartProbe.exe
.\scripts\test.ps1 -JdkHome 'C:\Program Files\Java\jdk-25' -JavaExe 'C:\Tools\jre8-x32\bin\java.exe' -Gui -RestartProbe build/UpdateRestartProbe.exe
```

Обязательные регрессии по затронутой области:

- `WeakCacheRollbackChecks` — очистка слабого кеша и откат без NPE.
- `SinglePassImportChecks` — совместимость XML, индексы, ошибка в конце, отмена и сохранность прежней БД.
- `SqliteShutdownChecks` — завершение и корректное поведение WAL/SHM.
- `DownloadChecks` — двухсекундная скорость, средняя, ETA, зависшие заголовки/тело ответа, ранняя/поздняя отмена и частичный ZIP.
- `DownloadUiChecks` — кнопка, Esc, крестик, успех и обрыв связи; интервал 1000 мс, очистка и сохранность БД/настроек/копии.
- `UpdateStorageChecks`, `ProgramUpdateUiChecks` — полный манифест копии без Java, отказ при повреждении файлов, сохранность последней копии и вызов очистки при настоящем старте.
- `UpdateHelperSmoke` — отдельный установщик, блокировка и перезапуск. Ждите полную запись маркера перезапуска, а не только появление файла.

Стандартные проверки используют 300 синтетических игроков и имитацию HTTPS, не реальный сервер. SAX-сообщение для намеренно ошибочного XML ожидаемо. GUI-тестам нужна графическая сессия; в их таймерах учитывайте вложенные модальные диалоги и ограничивайте время ожидания с завершением тестового процесса при сбое.

Для native-диагностики используйте проверки из `src/test/native` и `--check-runtime` на отдельной копии комплекта: этот параметр создаёт `data` и журналы. При изменении публикации/хранения релизов дополнительно выполните:

```powershell
python -m unittest discover -s src/test/python -p 'test_release_retention.py'
```

Для документации достаточно проверки ссылок, путей, примеров и соответствия коду; пересборка не нужна. Подробности: [сборка](docs/Сборка.md), [тестирование](docs/Тестирование.md).

### Реальное обновление и отчёты

`scripts/test-live-upgrade.py` — отдельная проверка с настоящим EXE и публичным GitHub. Проверьте `--help`, доступность целевого стабильного выпуска и наличие требуемых оригинальных ZIP с ожидаемыми SHA-256. Удалённый старый ZIP нельзя подменять новой пересборкой: восстановите сохранённый оригинал или укажите, почему прогон невозможен.

Используйте только новые профили в `.local`. Проверяйте оба комплекта, Java x32/x64 и путь с кириллицей/пробелами. Для политики хранения нужен `--require-storage-cleanup`; `--require-cleanup` относится к устаревшему документу и является отдельной проверкой.

Сравнивайте все строки/столбцы БД и историю, сохранённый при выходе старой версии `ttwr.cfg` с файлами при старте/выходе новой, все файлы последней копии и её исходный манифест, `runtime`, контрольные файлы, целостность и штатное завершение без WAL/SHM. Различайте начальную адаптацию геометрии искусственного профиля и изменение сохранённых настроек установщиком.

В переходе работает загрузчик исходной версии: обновление старой программы до версии с новым окном не проверяет это новое окно при самой загрузке. Не выдавайте имитацию HTTPS, проверку отдельных методов или отрисовку окна за реальный переход.

Для служебного наблюдения за CI используйте настроенную авторизацию API, не расходуя анонимный лимит, нужный программе. В реальном пользовательском прогоне не добавляйте авторизацию и не подменяйте ответы; при ограничении GitHub дождитесь восстановления доступа. Токены не выводятся, не сохраняются в документации и не передаются на адреса перенаправления загрузки.

Отчёт сохраняйте в `docs/validation/`: версии, среды, методика, фактический результат и ограничения. Подробные журналы, изображения и профили остаются в игнорируемых папках. Новые замеры отделяйте от исторических результатов; не обещайте ускорение или снижение памяти без измерений.

## Релизы и публикация

`.github/workflows/release.yml` по тегу `vX.Y.Z` собирает и проверяет оба ZIP на Windows, затем публикует релиз отдельной задачей. Ручной запуск создаёт артефакты без публикации. Перед тегом обновите `VERSION`, README, обе ссылки скачивания и раздел CHANGELOG; выполните `validate-release.ps1` и `check-public-tree.ps1`.

```powershell
.\scripts\package.ps1
.\scripts\package.ps1 -RuntimeHome 'C:\Tools\temurin-jre-25'
```

Первый комплект — без Java, второй — с полным JRE x64 и лицензиями. Готовые папки находятся в `dist`, ZIP — в `releases`; они не коммитятся в дерево исходников. Упаковка не заменяет существующие папки/архивы. Для повторной проверки используйте отдельный результат; для нового выпуска — новую версию.

При выпуске проверьте CI, публичный статус релиза, наличие обоих ZIP, скачивание без аккаунта, SHA-256, манифесты, встроенную версию и пустую базу. Успешная отправка тега ещё не означает успешной публикации. После ошибки CI сначала проверьте состояние релиза: сбой позднего шага возможен и после загрузки файлов.

Опубликованные ZIP и теги не заменяются. До публикации корректировать тег неудачной сборки можно после проверки отсутствия релиза и с защитой от изменения удалённого тега (`--force-with-lease`). Переписывание истории и массовое удаление веток/тегов не являются обычной подготовкой выпуска.

После успешной публикации текущий workflow запускает `prune-releases.py --keep 3`: остаются три новейших стабильных релиза, для более старых удаляются релизы, вложения и связанные теги. Черновики и предварительные выпуски защищены. Сохраняйте проверки целостности нового выпуска, повторную проверку перед удалением, защиту изменившегося тега и режим `--dry-run`. Не удаляйте выпуски отдельно от настроенной политики без задачи пользователя.

Сохраняйте сведения о сторонних компонентах и лицензии JRE. Не назначайте общую лицензию оригинальному TTWR без установленных прав; см. [THIRD_PARTY_NOTICES](THIRD_PARTY_NOTICES.md). Не включайте в Git реальные БД, настройки, пароли, журналы, кеш или локальные инструменты; исключение `vendor/upstream/ttwr.dat` не распространяется на остальные бинарники.

В сообщениях коммитов используйте глаголы совершенного вида, например «Добавил», «Исправил», «Обновил».

Не выполняйте push и публикацию без соответствующего запроса пользователя. При изменении поведения обновляйте документацию и CHANGELOG; при работе с бэклогом сохраняйте исходную постановку, уточняйте статус и актуализируйте указатель при переносе задачи в «Сделано». Инструкция выпуска: [GitHub Actions](docs/Автоматическая-сборка-и-публикация.md).

## Очистка локальных сборок

- Отличайте ZIP/распакованные комплекты в `releases`/`dist` от рабочих профилей, сохранённых данных и свидетельств проверки в `.local`. В частности, `.local/preserved-profiles` содержит сохранённые пользовательские профили.
- Перед удалением проверьте абсолютные пути, версии, наличие `data`, ссылки/junction и процессы, запущенные из выбранных папок. Рабочую программу пользователя ради очистки не завершайте.
- Если старый комплект содержит пользовательскую `data`, сначала сохраните её отдельно вместе со всеми файлами и проверьте копию/перенос по хешам. Сообщите новый путь. Не удаляйте WAL/SHM отдельно.
- Если задача не задаёт иное, оставляйте оба комплекта текущей версии из `VERSION`. После удаления старых ZIP актуализируйте локальный `SHA256SUMS.txt` и проверьте оставшиеся архивы.
- Для обратимой очистки используйте Корзину. Перемещение в неё не освобождает место на диске до её очистки; не сообщайте обратное.
- Не применяйте общую очистку `build`, `dist`, `.local` или `git clean -xfd` для обхода ошибки сборки. Не удаляйте исходники, резервные копии, профили и отчёты как «старые сборки» без проверки их назначения.
